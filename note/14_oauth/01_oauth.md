# OAuth 2.0이란 무엇인가

> 인증, 인가, 토큰의 기본 개념은 [인증과 인가](../12_spring_security/01_authentication_and_authorization.md), [세션 기반 인증과 토큰 기반 인증](../13_jwt/01_session_vs_token_auth.md)에서 설명했다.

## 1. 해결하려는 문제
블로그 서비스가 사용자의 Google 계정 이메일과 이름을 알아야 한다고 하자. 가장 단순한 방법은 사용자에게 Google 아이디와 비밀번호를 받아서 블로그 서버가 대신 Google에 로그인하는 것이다. 이 방법에는 다음 문제가 있다.

| 문제 | 설명 |
|---|---|
| 비밀번호 노출 | 블로그 서버가 사용자의 Google 비밀번호를 알게 된다. 블로그 서버가 해킹되면 Google 계정까지 넘어간다. |
| 권한 범위를 제한할 수 없다 | 비밀번호를 가진 쪽은 이메일 읽기뿐 아니라 메일 삭제, 결제 등 계정의 모든 일을 할 수 있다. |
| 권한을 일부만 회수할 수 없다 | 블로그 서비스만 접근을 끊으려면 Google 비밀번호를 바꾸는 수밖에 없고, 그러면 그 비밀번호를 쓰던 다른 모든 곳도 끊긴다. |
| 다중 인증과 충돌 | Google 계정에 2단계 인증이 켜져 있으면 비밀번호만으로는 로그인할 수 없다. |

**OAuth 2.0**은 이 문제를 해결한다. 사용자는 비밀번호를 **Google에만** 입력하고, Google이 블로그 서버에게 **"이 사용자의 이메일과 프로필만 읽을 수 있는 권한"**을 담은 **액세스 토큰**을 발급한다.

## 2. 정의
**OAuth 2.0은 사용자가 자신의 비밀번호를 넘기지 않고, 제3의 애플리케이션이 자신의 데이터에 제한된 범위로 접근하도록 허락하는 권한 위임(Delegated Authorization) 프레임워크**다. RFC 6749에 정의되어 있다.

> **위임(Delegation)이란?**
> 자신이 가진 권한의 일부를 다른 주체가 대신 쓸 수 있게 넘겨주는 것이다. OAuth에서는 사용자가 "내 Google 프로필을 읽을 권한"을 블로그 서버에게 넘겨준다.

이름의 "Auth"는 **Authorization(인가)**이다. OAuth는 원래 **"무엇에 접근할 수 있는가"**를 다루는 표준이고, **"누구인가"(인증)**를 다루는 표준이 아니다. 로그인(인증)에 쓰려면 4장의 방법이 필요하다.

## 3. 네 가지 역할
OAuth 2.0은 참여자를 네 가지 역할로 나눈다.

| 역할 | 정의 | 이 프로젝트에서 |
|---|---|---|
| **리소스 소유자** (Resource Owner) | 보호된 데이터의 주인. 접근을 허락하는 사람 | 블로그에 Google로 로그인하는 사용자 |
| **클라이언트** (Client) | 리소스 소유자의 허락을 받아 데이터에 접근하려는 애플리케이션 | 블로그 백엔드 서버 (Spring Boot) |
| **인가 서버** (Authorization Server) | 리소스 소유자를 인증하고, 허락을 받아 클라이언트에게 토큰을 발급하는 서버 | `accounts.google.com`, `oauth2.googleapis.com` |
| **리소스 서버** (Resource Server) | 보호된 데이터를 가지고 있고, 액세스 토큰을 확인해 데이터를 주는 서버 | Google 사용자 정보 API (`www.googleapis.com/oauth2/v3/userinfo`) |

"클라이언트"가 브라우저가 아니라 **블로그 서버**라는 점에 주의한다. OAuth에서 클라이언트는 "데이터를 요청하는 애플리케이션"을 뜻한다. 브라우저는 사용자가 인가 서버와 대화하는 통로인 **사용자 에이전트(User-Agent)**다.

```
              리소스 소유자 (사용자)
                    │ 브라우저 (User-Agent)
        ┌───────────┴───────────┐
        ▼                       ▼
  클라이언트 ◀── 토큰 발급 ── 인가 서버
  (블로그 서버)                (Google 계정)
        │
        └── 액세스 토큰으로 요청 ──▶ 리소스 서버
                                   (Google 사용자 정보 API)
```

## 4. OAuth 2.0과 로그인: OpenID Connect
OAuth 2.0의 결과물인 액세스 토큰은 "이 클라이언트가 이 데이터에 접근해도 된다"는 증명이다. "이 토큰을 가진 사람이 누구인가"를 클라이언트에게 알려 주는 것이 목적이 아니다.

그래서 OAuth로 로그인을 구현하는 방법은 두 가지다.

| 방법 | 동작 | 이 프로젝트 |
|---|---|---|
| OAuth 2.0 + 사용자 정보 API | 액세스 토큰으로 사용자 정보 API를 호출해서 받은 이메일로 사용자를 식별한다. | **이 방식** (`scope`: `email`, `profile`) |
| **OpenID Connect (OIDC)** | OAuth 2.0 위에 "인증" 기능을 표준으로 얹은 규격. `scope`에 `openid`를 넣으면 인가 서버가 액세스 토큰과 함께 **ID 토큰**(사용자 정보가 담긴 JWT)을 준다. | 사용하지 않음 |

> **ID 토큰이란?**
> OpenID Connect에서 인가 서버가 발급하는 JWT다. `iss`(발급자), `sub`(사용자 고유 번호), `aud`(이 토큰을 받을 클라이언트의 Client ID), `exp`, `iat`, `email` 등이 들어 있다. 클라이언트는 서명을 검증하는 것만으로 사용자를 확인할 수 있다([JWT의 구조](../13_jwt/04_jwt_structure.md)).

Spring Security는 `scope`에 `openid`가 있으면 `OidcUserService`, 없으면 `DefaultOAuth2UserService`로 사용자 정보를 처리한다. 이 프로젝트의 `OAuth2UserCustomService`는 `DefaultOAuth2UserService`를 상속하므로, `scope`에 `openid`를 추가하면 이 클래스가 호출되지 않는다는 점에 주의한다.

## 5. 권한 부여 방식 (Grant Type)
클라이언트가 액세스 토큰을 받는 방법을 **권한 부여 방식(Grant Type)**이라고 한다.

| 방식 | 흐름 | 쓰는 경우 | 현재 권장 여부 |
|---|---|---|---|
| **권한 부여 코드 (Authorization Code)** | 사용자 동의 → 인가 서버가 **코드**를 줌 → 클라이언트가 코드를 **토큰으로 교환** | 서버가 있는 웹 애플리케이션. PKCE와 함께 SPA, 모바일 앱 | **권장** |
| 암묵적 (Implicit) | 사용자 동의 → 인가 서버가 **토큰을 바로** 브라우저 URL로 줌 | 예전 SPA | 사용 중단 권고 (토큰이 URL에 노출) |
| 리소스 소유자 비밀번호 (Password) | 사용자의 아이디, 비밀번호를 클라이언트가 받아서 토큰 요청 | 인가 서버와 클라이언트가 같은 회사의 신뢰된 앱 | 사용 중단 권고 (1장의 문제 그대로) |
| 클라이언트 자격 증명 (Client Credentials) | 사용자 없이 클라이언트가 자기 자신의 자격으로 토큰 요청 | 서버끼리 통신 | 권장 (사용자 데이터가 아닐 때) |
| 리프레시 토큰 (Refresh Token) | 리프레시 토큰으로 새 액세스 토큰 요청 | 액세스 토큰 만료 시 | 권장 |
| 디바이스 코드 (Device Code) | TV 같은 입력이 불편한 기기에서 다른 기기로 동의 | 스마트 TV, CLI 도구 | 권장 |

OAuth 2.1(작성 중인 개정판)은 암묵적 방식과 비밀번호 방식을 제거하고, 권한 부여 코드 방식에 PKCE를 필수로 한다.

이 프로젝트가 쓰는 **권한 부여 코드 방식**은 [권한 부여 코드 승인 방식](./02_authorization_code_grant.md)에서 요청 메시지 단위로 자세히 본다.

## 6. 액세스 토큰과 범위 (Scope)
**액세스 토큰**은 "이 클라이언트가 이 사용자의 이 범위 데이터에 접근해도 된다"는 증명이다. 리소스 서버에 요청할 때 `Authorization: Bearer <액세스 토큰>` 헤더로 보낸다.

**범위(Scope)**는 클라이언트가 요청하는 권한의 종류다. 인가 서버가 정의하고, 동의 화면에 사용자가 읽을 수 있는 문장으로 표시된다.

| Google scope | 동의 화면 표시 | 접근 가능한 정보 |
|---|---|---|
| `email` | 이메일 주소 보기 | `email`, `email_verified` |
| `profile` | 개인정보(공개 프로필 포함) 보기 | `name`, `given_name`, `family_name`, `picture` |
| `openid` | Google에서 내 개인 정보를 나와 연결 | ID 토큰 발급, `sub` |
| `https://www.googleapis.com/auth/drive.readonly` | Google Drive 파일 보기 | Drive 파일 읽기 |

클라이언트는 **필요한 최소한의 범위**만 요청해야 한다. 범위가 클수록 사용자가 동의를 거부할 가능성이 커지고, 토큰이 유출됐을 때 피해도 커진다.

## 정리
| 항목 | 핵심 |
|---|---|
| 목적 | 비밀번호를 넘기지 않고 제한된 범위의 접근 권한을 위임 |
| 역할 | 리소스 소유자(사용자), 클라이언트(블로그 서버), 인가 서버, 리소스 서버(Google) |
| 결과물 | 범위가 제한된 액세스 토큰 |
| 로그인 | OAuth는 인가 표준. 로그인에는 사용자 정보 API 또는 OpenID Connect(ID 토큰)를 쓴다 |
| 권장 방식 | 권한 부여 코드 방식 (+ PKCE) |
