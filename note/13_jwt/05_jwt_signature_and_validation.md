# JWT의 서명과 검증

> JWT의 구조와 Base64URL은 [JWT의 구조](./04_jwt_structure.md)에서 설명했다.
> 이 노트의 예시 값은 그 노트와 같다: 비밀 키 `my-blog-secret-key-must-be-at-least-32-bytes!!`(46바이트), HS256.

## 1. 서명에 필요한 두 가지 도구

### 해시 함수 (Hash Function)
> **해시 함수란?**
> 길이에 상관없는 입력을 받아 **고정된 길이**의 값(해시값, 다이제스트)을 만드는 함수다.

서명에 쓰는 **암호학적 해시 함수**는 다음 성질을 갖는다.

| 성질 | 의미 |
|---|---|
| 결정성 | 같은 입력은 항상 같은 출력 |
| 단방향성 | 출력으로부터 입력을 계산해 낼 수 없다 |
| 충돌 저항성 | 같은 출력을 내는 서로 다른 두 입력을 찾을 수 없다 |
| 눈사태 효과 | 입력이 1비트만 달라도 출력 비트의 약 절반이 바뀐다 |

**SHA-256**은 입력을 512비트(64바이트) 블록 단위로 처리해서 256비트(32바이트) 해시값을 만든다. 입력 길이가 64바이트의 배수가 아니면 다음과 같이 채운 뒤 처리한다.
```
[원래 메시지] [1비트 '1'] [필요한 만큼 '0'] [원래 메시지 길이(비트 수)를 64비트로]
└──────────────────── 전체 길이가 512비트의 배수가 되도록 ────────────────────┘
```

### 비밀 키 없이 해시만 쓰면 안 되는 이유
`서명 = SHA-256(헤더.페이로드)`로 하면 어떻게 될까? SHA-256은 공개된 알고리즘이라 **누구나 계산할 수 있다.** 공격자가 페이로드를 바꾸고 해시를 다시 계산해 붙이면 서버는 위조를 알아챌 수 없다.

그래서 **서버만 아는 비밀 키를 섞어서** 계산해야 한다. 이것이 **MAC(Message Authentication Code)**이고, 해시 함수로 MAC을 만드는 표준 방법이 **HMAC**이다.

## 2. HMAC-SHA256 (`HS256`)의 내부 동작
RFC 2104에 정의되어 있다.
```
HMAC(K, m) = H( (K' ⊕ opad) ‖ H( (K' ⊕ ipad) ‖ m ) )
```
| 기호 | 의미 |
|---|---|
| `H` | 해시 함수 (SHA-256) |
| `K` | 비밀 키 |
| `K'` | 블록 크기(64바이트)에 맞춘 키. `K`가 64바이트보다 길면 `H(K)`(32바이트)로 줄이고, 그 뒤 64바이트가 될 때까지 `0x00`을 붙인다. |
| `ipad` | `0x36`을 64번 반복한 64바이트 |
| `opad` | `0x5C`를 64번 반복한 64바이트 |
| `⊕` | XOR (비트마다 같으면 0, 다르면 1) |
| `‖` | 바이트를 이어 붙이기 |
| `m` | 서명할 메시지 (JWT의 서명 입력) |

### 예시 값으로 따라가기
**1단계. `K'` 만들기**
```
K  = "my-blog-secret-key-must-be-at-least-32-bytes!!"   (46바이트)
K' = K + 0x00 × 18                                      (64바이트)
```
46바이트는 64바이트보다 짧으므로 해시하지 않고 뒤에 `0x00`을 붙인다.

**2단계. 안쪽 해시**
```
K' ⊕ ipad   : 키의 각 바이트를 0x36과 XOR      (64바이트)
              예) 'm' 0x6D ⊕ 0x36 = 0x5B
m           : "eyJ0eXAi...JIUzI1NiJ9.eyJpc3Mi...aWQiOjF9"   (149바이트)
안쪽 입력    : (K' ⊕ ipad) ‖ m                  (213바이트)
안쪽 해시    : SHA-256(안쪽 입력)                (32바이트)
```
213바이트 = 1704비트. 채우기를 하면 `1704 + 1 + 0의 개수 + 64`가 512의 배수가 되어야 하므로 2048비트, 즉 **블록 4개**를 처리한다.

**3단계. 바깥쪽 해시**
```
K' ⊕ opad   : 키의 각 바이트를 0x5C와 XOR      (64바이트)
바깥 입력    : (K' ⊕ opad) ‖ 안쪽 해시           (96바이트)
HMAC 결과    : SHA-256(바깥 입력)                (32바이트)
```
96바이트 = 768비트 → 채우면 1024비트, **블록 2개**.

**결과**
```
41 1c ba a3 d7 33 82 65 99 c0 94 ca d3 0b 3b 53
2b 5c c7 03 ce 9e 88 aa 20 67 a8 e9 76 a9 45 74
→ Base64URL: QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ
```

### 왜 해시를 두 번 하는가
`H(K ‖ m)`처럼 한 번만 하면 SHA-256의 구조 때문에 **길이 확장 공격**이 가능하다. 공격자가 `H(K ‖ m)` 값과 `m`의 길이만 알면, 키를 모르고도 `H(K ‖ m ‖ 추가 데이터)`를 계산할 수 있다. 바깥에서 키를 섞어 한 번 더 해시하면 이 공격이 막힌다. `ipad`와 `opad`를 다르게 해서 안쪽과 바깥쪽 키가 서로 다른 값이 되게 한다.

### 키 길이 요구 사항
RFC 7518 3.2절: **HS256의 키는 해시 출력 크기(256비트 = 32바이트) 이상이어야 한다.**

짧은 키는 공격자가 **오프라인 대입 공격**으로 찾아낼 수 있다. 공격자는 토큰 하나만 있으면 된다.
```
for 후보 in 키 후보 목록:
    if HMAC-SHA256(후보, 헤더.페이로드) == 토큰의 서명:
        비밀 키 발견 → 이제 아무 토큰이나 만들 수 있다
```
서버에 요청을 보낼 필요가 없으므로 서버가 막을 방법도 없다. 그래서 키는 **사람이 정한 단어가 아니라 보안 난수로 만든 32바이트 이상의 값**이어야 한다.
```bash
openssl rand -base64 32     # 32바이트 난수를 Base64로 출력
```

## 3. 비대칭 서명 (`RS256`, `ES256`)
HMAC은 서명하는 키와 검증하는 키가 **같다**(대칭). 그래서 검증하는 서버도 토큰을 만들 수 있다.

**비대칭 서명**은 키가 두 개다.

| 키 | 가진 곳 | 하는 일 |
|---|---|---|
| 개인 키 (Private Key) | 토큰을 발급하는 인증 서버만 | 서명 생성 |
| 공개 키 (Public Key) | 누구나 (검증하는 모든 서버) | 서명 검증 |

공개 키로는 서명을 **검증만** 할 수 있고 **만들 수는 없다.** 그래서 공개 키를 마음껏 나눠 줘도 된다.

### RS256 (RSASSA-PKCS1-v1_5 + SHA-256)
```
서명:  1. h = SHA-256(서명 입력)                                  (32바이트)
       2. h 앞에 "SHA-256을 썼다"는 표시(DER 인코딩, 19바이트)를 붙임
       3. 앞을 0x00 0x01 0xFF...0xFF 0x00 으로 채워 키 길이(256바이트)로 맞춤
       4. 개인 키로 RSA 연산: s = 위 값^d mod n                   (256바이트)
검증:  1. 공개 키로 RSA 연산: s^e mod n
       2. 결과에서 h를 꺼내 SHA-256(서명 입력)과 비교
```
2048비트 키의 서명은 256바이트 → Base64URL 342글자. 토큰이 HS256보다 300글자 정도 길어진다.

### ES256 (ECDSA P-256 + SHA-256)
타원 곡선 암호를 쓴다. RSA보다 짧은 키로 같은 안전성을 낸다. 서명은 `R`(32바이트) ‖ `S`(32바이트) = 64바이트 → Base64URL 86글자.

### 공개 키 배포: JWKS
인증 서버는 보통 공개 키 목록을 JSON으로 공개한다(JWK Set).
```http
GET /.well-known/jwks.json

{"keys":[{"kty":"RSA","kid":"2026-10","use":"sig","alg":"RS256","n":"0vx7ago...","e":"AQAB"}]}
```
토큰 헤더의 `kid`를 보고 이 목록에서 같은 `kid`의 키를 골라 검증한다. 키를 바꿀 때는 새 키를 목록에 추가하고, 기존 토큰이 모두 만료된 뒤 옛 키를 뺀다.

### 언제 무엇을 쓰나
| | HS256 | RS256 / ES256 |
|---|---|---|
| 키 | 비밀 키 1개를 공유 | 개인 키 1개 + 공개 키 |
| 검증하는 쪽도 토큰을 만들 수 있나 | 있다 | 없다 |
| 속도 | 매우 빠르다 | 상대적으로 느리다 (특히 RSA 서명) |
| 적합한 경우 | 발급과 검증을 같은 서버(또는 같은 팀의 서버들)가 할 때 | 발급하는 곳과 검증하는 곳이 다를 때 (인증 서버 + 여러 서비스, 외부 서비스) |

## 4. 검증 절차
RFC 7515 5.2절과 RFC 7519 7.2절을 바탕으로, 서버가 토큰을 받았을 때 해야 할 일을 순서대로 정리하면 다음과 같다.
```
입력: "eyJ0eXAi...JIUzI1NiJ9.eyJpc3Mi...aWQiOjF9.QRy6o9cz...apRXQ"
```

**1. 형식 확인**
점(`.`)으로 나눠서 정확히 3부분인지 확인한다. 각 부분이 Base64URL 문자로만 이루어졌는지 확인한다.
```
[0] eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9
[1] eyJpc3MiOiJpc3N1ZUBh...aWQiOjF9
[2] QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ
```

**2. 헤더 해석**
[0]을 Base64URL 디코딩해서 JSON으로 읽는다.
```json
{"typ":"JWT","alg":"HS256"}
```

**3. 알고리즘 확인**
`alg`가 **서버가 미리 정해 둔 알고리즘**과 같은지 확인한다. 토큰이 말하는 알고리즘을 그대로 믿으면 안 된다(5장).

**4. 서명 다시 계산**
받은 [0] + `.` + [1] **문자열 그대로**를 서명 입력으로 해서, 서버의 키로 서명을 계산한다.
```
HMAC-SHA256(비밀 키, "eyJ0eXAi...JIUzI1NiJ9.eyJpc3Mi...aWQiOjF9")
→ 41 1c ba a3 ... 45 74
```

**5. 서명 비교**
[2]를 Base64URL 디코딩한 32바이트와 4번 결과를 비교한다. **비교는 고정 시간(constant-time)으로 한다.**

> **고정 시간 비교란?**
> 두 값이 어디서 다르든 항상 같은 시간이 걸리게 비교하는 방법이다. 보통의 비교는 첫 번째로 다른 바이트에서 바로 멈춘다. 그러면 "앞쪽 몇 바이트가 맞았는지"에 따라 응답 시간이 달라지고, 공격자가 시간을 재서 서명을 한 바이트씩 맞혀 나갈 수 있다. Java에서는 `MessageDigest.isEqual()`이 고정 시간 비교다.

다르면 **위조** → 거부.

**6. 페이로드 해석**
서명이 맞으면 [1]을 Base64URL 디코딩해서 JSON으로 읽는다. **서명 확인 전에 페이로드 내용을 믿고 쓰면 안 된다.**

**7. 클레임 검증**
| 클레임 | 검사 | 실패 시 |
|---|---|---|
| `exp` | `현재 시각 < exp + 여유` | 만료 → 거부 |
| `nbf` (있으면) | `현재 시각 >= nbf - 여유` | 아직 사용 불가 → 거부 |
| `iss` | 기대하는 발급자와 같은가 | 다른 곳에서 발급 → 거부 |
| `aud` (있으면) | 자기 자신이 포함되어 있는가 | 다른 서비스용 토큰 → 거부 |

예시 토큰을 2026-10-03 13:00 KST(= 1791000000)에 검증하면 `1791000000 < 1791003600`이므로 통과. 14:00:01(= 1791003601)에 검증하면 만료로 거부된다.

**8. 사용**
`sub`, `id` 등으로 사용자를 식별해서 요청을 처리한다.

## 5. 알려진 공격과 방어

### `alg: none` 공격
공격자가 헤더를 `{"alg":"none"}`으로 바꾸고 서명을 비운다.
```
eyJhbGciOiJub25lIn0.eyJzdWIiOiJhZG1pbiJ9.
```
검증 코드가 헤더의 `alg`를 그대로 따르면 "서명 없음"으로 처리해서 통과시킨다.

**방어:** 3단계에서 서버가 정한 알고리즘만 허용한다. 서명이 없는 토큰은 거부한다.

### 알고리즘 혼동 공격 (RS256 → HS256)
서버는 RS256을 쓰고, 공개 키는 누구나 알 수 있다. 공격자가:
1. 헤더를 `{"alg":"HS256"}`으로 바꾼다.
2. **공개 키 파일의 내용을 HMAC 비밀 키로 써서** 서명을 만든다.
3. 서버의 검증 코드가 헤더의 `alg`를 보고 HS256으로 검증하면서, 키 자리에 원래 쓰던 공개 키를 넣는다.
4. 공격자가 만든 서명과 일치 → 통과

**방어:** 3단계와 같다. 알고리즘은 토큰이 아니라 서버 설정으로 정한다. 키와 알고리즘을 한 쌍으로 묶어 관리한다.

### 약한 비밀 키
2장의 오프라인 대입 공격. **방어:** 보안 난수로 만든 32바이트 이상의 키.

### 토큰 탈취
토큰을 훔친 사람은 그 토큰으로 로그인한 것과 같다. 서명은 "누가 보냈는지"를 확인하지 않는다.

**방어:** HTTPS, 짧은 만료 시간, 안전한 저장 위치([토큰 기반 인증의 흐름과 HTTP 메시지 형식](./02_token_auth_flow_and_http_message.md) 5장), 리프레시 토큰 교체([리프레시 토큰](./06_refresh_token.md)).

### 민감 정보 노출
페이로드는 누구나 읽을 수 있다. **방어:** 비밀번호, 개인정보를 넣지 않는다.

이런 주의 사항들은 RFC 8725(JWT Best Current Practices)에 정리되어 있다.

## 6. 직접 구현하지 않는다
위 절차를 직접 코드로 짜면 고정 시간 비교, `alg` 검사, 시계 오차 처리 같은 부분을 빠뜨리기 쉽다. 검증된 라이브러리를 쓴다.

| 언어 | 라이브러리 |
|---|---|
| Java | jjwt (`io.jsonwebtoken`), Nimbus JOSE + JWT (Spring Security가 내부에서 사용) |
| JavaScript | `jose`, `jsonwebtoken` |

이 프로젝트가 쓰는 jjwt 0.9.1에서 검증은 다음 한 줄이다.
```java
Jwts.parser()
        .setSigningKey(비밀 키)
        .parseClaimsJws(token);   // 1~7단계를 수행. 실패하면 예외
```
| 실패 원인 | jjwt 0.9.1의 예외 |
|---|---|
| 형식 오류 | `MalformedJwtException` |
| 서명 불일치 | `SignatureException` |
| 만료 | `ExpiredJwtException` |
| 서명 없는 토큰 (`alg: none`) | `UnsupportedJwtException` |
| `null` 또는 빈 문자열 | `IllegalArgumentException` |

`parseClaimsJws()`는 이름 그대로 **서명된(JWS)** 토큰만 받아들이므로, `alg: none` 토큰은 거부된다.

## 정리
| 항목 | 핵심 |
|---|---|
| HS256 | `HMAC-SHA256(비밀 키, 인코딩된 헤더.페이로드)`. 키로 두 번 해시해서 길이 확장 공격을 막는다 |
| 키 길이 | HS256은 32바이트 이상의 난수 |
| RS256 / ES256 | 개인 키로 서명, 공개 키로 검증. 발급처와 검증처가 다를 때 |
| 검증 순서 | 형식 → 헤더 → **알고리즘 고정** → 서명 재계산 → **고정 시간 비교** → 페이로드 → `exp`/`iss`/`aud` |
| 주요 공격 | `alg: none`, 알고리즘 혼동, 약한 키, 탈취 |
