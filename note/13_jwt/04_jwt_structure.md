# JWT의 구조 - 헤더, 페이로드, 서명과 Base64URL

> 토큰 기반 인증의 흐름은 [토큰 기반 인증의 흐름과 HTTP 메시지 형식](./02_token_auth_flow_and_http_message.md)에서 설명했다.

## 1. JWT란
**JSON Web Token.** 두 당사자 사이에서 주고받을 정보(클레임)를 **JSON**으로 표현하고, 그 정보가 바뀌지 않았음을 **서명**으로 보장하는 **URL에 안전한 문자열** 형식이다. RFC 7519에 정의되어 있다. 읽을 때는 보통 "젓(jot)"이라고 발음한다.

JWT는 혼자 정의된 형식이 아니라 여러 표준이 함께 쓰인다.

| 표준 | 이름 | 정하는 것 |
|---|---|---|
| RFC 7519 | JWT (JSON Web Token) | 클레임의 형식과 의미 |
| RFC 7515 | JWS (JSON Web Signature) | **서명된** 토큰의 형식과 서명 방법 |
| RFC 7516 | JWE (JSON Web Encryption) | **암호화된** 토큰의 형식 |
| RFC 7518 | JWA (JSON Web Algorithms) | `HS256`, `RS256` 같은 알고리즘 이름과 사용법 |
| RFC 7517 | JWK (JSON Web Key) | 키를 JSON으로 표현하는 형식 |
| RFC 4648 | Base64 / Base64URL | 바이트를 문자로 바꾸는 인코딩 |

JWT는 JWS 또는 JWE의 형식에 담긴다.

| | JWS | JWE |
|---|---|---|
| 보장하는 것 | 무결성 (바뀌지 않음) | 무결성 + 기밀성 (읽을 수 없음) |
| 점(`.`)으로 나뉜 부분 | 3개 | 5개 |
| 내용을 읽을 수 있나 | 누구나 읽을 수 있다 | 키가 있어야 읽을 수 있다 |
| 사용 빈도 | **대부분 이것** | 내용을 숨겨야 할 때만 |

**일반적으로 "JWT"라고 하면 JWS 형식의 JWT를 말한다.** 이 노트도 JWS를 기준으로 한다.

## 2. 전체 구조
```
헤더 . 페이로드 . 서명
```
세 부분을 각각 **Base64URL**로 인코딩하고 점(`.`, `0x2E`)으로 잇는다. 이 형태를 **JWS Compact Serialization**이라고 한다.

이 노트에서 계속 쓸 예시 토큰(실제로 계산한 값):
```
eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJpc3N1ZUBhbnRpbW9ueS5rciIsImlhdCI6MTc5MDk5NjQwMCwiZXhwIjoxNzkxMDAzNjAwLCJzdWIiOiJhQGEuY29tIiwiaWQiOjF9.QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ
```
| 부분 | Base64URL 문자열 | 길이 | 디코딩한 원본 | 원본 크기 |
|---|---|---|---|---|
| 헤더 | `eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9` | 36글자 | `{"typ":"JWT","alg":"HS256"}` | 27바이트 |
| 페이로드 | `eyJpc3MiOiJpc3N1ZUBh...aWQiOjF9` | 112글자 | `{"iss":"issue@antimony.kr","iat":1790996400,"exp":1791003600,"sub":"a@a.com","id":1}` | 84바이트 |
| 서명 | `QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ` | 43글자 | `41 1c ba a3 ... 45 74` (이진 데이터) | 32바이트 |
| 전체 | | **193글자** (36 + 1 + 112 + 1 + 43) | | |

예시 값의 조건: 비밀 키 `my-blog-secret-key-must-be-at-least-32-bytes!!`(46바이트), 발급 2026-10-03 12:00:00 KST, 유효 시간 2시간.

거의 모든 JWT가 `eyJ`로 시작하는 이유: 헤더는 JSON이라 `{"`로 시작하고 그 뒤에 영문 소문자 파라미터 이름(`typ`, `alg`)이 온다. 이 세 바이트를 Base64URL로 바꾸면 앞의 세 글자가 `eyJ`가 된다(3장에서 계산).

## 3. Base64URL 인코딩

### 왜 인코딩이 필요한가
- 서명은 이진 데이터다. `0x00`, `0x0D`(CR), `0x0A`(LF) 같은 바이트가 들어 있을 수 있는데, 이것을 HTTP 헤더에 그대로 넣으면 헤더 줄이 끝난 것으로 해석된다.
- JSON에는 `"`, 공백, 한글 등이 들어 있어서 URL이나 헤더에 그대로 넣기 어렵다.
- 그래서 **어떤 바이트든 안전한 64개 문자로만 표현**하는 Base64 인코딩을 쓴다.

### Base64의 원리
**3바이트(24비트)를 6비트씩 4조각으로 나누고, 각 조각(0~63)을 문자 하나로 바꾼다.**
```
입력 3바이트 = 24비트
┌────────┬────────┬────────┐
│ 바이트1 │ 바이트2 │ 바이트3 │
└────────┴────────┴────────┘
┌──────┬──────┬──────┬──────┐
│ 6비트 │ 6비트 │ 6비트 │ 6비트 │  → 문자 4개
└──────┴──────┴──────┴──────┘
```
6비트로 나타낼 수 있는 값은 2^6 = 64가지이므로 문자 64개가 필요하다. 그래서 출력은 입력보다 4/3배 길어진다.

### 문자표
| 값 | 문자 | 값 | 문자 | 값 | 문자 | 값 | 문자 |
|---|---|---|---|---|---|---|---|
| 0–25 | `A`–`Z` | 26–51 | `a`–`z` | 52–61 | `0`–`9` | 62 | `+` (Base64) / **`-`** (Base64URL) |
| | | | | | | 63 | `/` (Base64) / **`_`** (Base64URL) |

### Base64와 Base64URL의 차이
| | Base64 (RFC 4648 4장) | Base64URL (RFC 4648 5장) |
|---|---|---|
| 62번 문자 | `+` | `-` |
| 63번 문자 | `/` | `_` |
| 패딩 `=` | 붙인다 | **JWT에서는 붙이지 않는다** |

`+`, `/`, `=`는 URL에서 특별한 의미가 있다(`+`는 공백, `/`는 경로 구분, `=`는 파라미터 값 구분). Base64URL은 이 문자들을 피해서 토큰을 URL이나 헤더에 그대로 넣을 수 있게 한다.
```
바이트 FB FF BF → 11111011 11111111 10111111
6비트 조각      → 111110 111111 111110 111111 = 62, 63, 62, 63
Base64          → +/+/
Base64URL       → -_-_
```

### 실제 계산: 헤더의 첫 6바이트
헤더 JSON `{"typ":"JWT","alg":"HS256"}`의 처음 6바이트 `{"typ"`를 인코딩한다.

**첫 번째 3바이트 `{"t`**
```
문자         {          "          t
바이트       0x7B       0x22       0x74
비트         01111011   00100010   01110100

6비트로 다시 나눔
             011110 | 110010 | 001001 | 110100
값           30       50       9        52
문자         e        y        J        0
```
**두 번째 3바이트 `yp"`**
```
문자         y          p          "
바이트       0x79       0x70       0x22
비트         01111001   01110000   00100010

6비트로 다시 나눔
             011110 | 010111 | 000000 | 100010
값           30       23       0        34
문자         e        X        A        i
```
결과 `eyJ0eXAi`가 헤더 Base64URL 문자열의 앞부분과 일치한다.

### 남는 바이트가 있을 때 (패딩)
입력 길이가 3의 배수가 아니면 마지막 조각이 모자란다. 모자란 비트는 `0`으로 채운다.

**2바이트 `id`가 남았을 때**
```
바이트       0x69       0x64
비트         01101001   01100100   (00 ← 0으로 채움)
6비트        011010 | 010110 | 010000
값           26       22       16
문자         a        W        Q
Base64       aWQ=      ← 4글자를 맞추려고 = 를 붙임
Base64URL    aWQ       ← JWT는 = 를 붙이지 않음
```
| 남은 바이트 | 출력 문자 수 | Base64 패딩 |
|---|---|---|
| 0 (3의 배수) | 4의 배수 | 없음 |
| 1 | 2글자 | `==` |
| 2 | 3글자 | `=` |

예시 토큰의 서명은 32바이트다. 32 = 3 × 10 + 2이므로 2바이트가 남는다. 일반 Base64로는 `QRy6...RXQ=`(44글자)이고, JWT에서는 `=`를 뺀 43글자가 된다. 헤더(27바이트)와 페이로드(84바이트)는 3의 배수라서 원래 패딩이 없다.

디코딩할 때는 반대로, 글자 수를 4로 나눈 나머지를 보고 `=`를 다시 붙인 것으로 생각해서 계산한다.

### Base64는 암호화가 아니다
Base64는 정해진 표에 따라 바꾸는 것일 뿐이다. 키가 없고, 누구나 원래대로 되돌릴 수 있다. JWT의 헤더와 페이로드는 **누구나 읽을 수 있다.**

## 4. 헤더 (JOSE Header)
토큰을 **어떻게 처리해야 하는지** 알려 주는 JSON이다. JOSE(JSON Object Signing and Encryption) 헤더라고 부른다.
```json
{"typ":"JWT","alg":"HS256"}
```

### 헤더 파라미터
| 파라미터 | 이름 | 필수 | 의미 |
|---|---|---|---|
| `alg` | Algorithm | **필수** | 서명 알고리즘. `HS256`, `RS256`, `ES256` 등 |
| `typ` | Type | 선택 | 이 토큰의 종류. JWT면 `"JWT"` |
| `kid` | Key ID | 선택 | 어떤 키로 서명했는지 가리키는 이름. 키를 여러 개 쓰거나 교체할 때 검증할 키를 고르는 데 쓴다. |
| `cty` | Content Type | 선택 | 페이로드가 또 다른 JWT일 때(중첩) `"JWT"` |
| `jku` | JWK Set URL | 선택 | 검증용 공개 키 목록을 받을 수 있는 URL |
| `jwk` | JSON Web Key | 선택 | 검증용 공개 키 자체 |
| `x5u`, `x5c`, `x5t` | X.509 관련 | 선택 | 인증서로 키를 전달할 때 |
| `crit` | Critical | 선택 | "이 확장 파라미터를 이해하지 못하면 토큰을 거부하라"는 목록 |

### 주요 `alg` 값
| 값 | 방식 | 서명 키 | 검증 키 | 서명 크기 |
|---|---|---|---|---|
| `HS256` | HMAC + SHA-256 | 비밀 키 | **같은** 비밀 키 | 32바이트 |
| `HS384`, `HS512` | HMAC + SHA-384/512 | 비밀 키 | 같은 비밀 키 | 48, 64바이트 |
| `RS256` | RSA 서명 + SHA-256 | RSA 개인 키 | RSA 공개 키 | 키 길이와 같음 (2048비트 키 → 256바이트) |
| `ES256` | ECDSA P-256 + SHA-256 | EC 개인 키 | EC 공개 키 | 64바이트 |
| `none` | 서명 없음 | - | - | 0바이트 |

`none`은 표준에 있지만 **인증 용도로는 절대 받아들이면 안 된다**([JWT의 서명과 검증](./05_jwt_signature_and_validation.md)).

## 5. 페이로드 (Claims Set)
토큰이 전달하는 **정보**를 담은 JSON이다. 각 `이름: 값` 쌍을 **클레임(Claim)**이라고 한다.
```json
{
  "iss": "issue@antimony.kr",
  "iat": 1790996400,
  "exp": 1791003600,
  "sub": "a@a.com",
  "id": 1
}
```
실제 토큰에서는 공백과 줄바꿈 없이 한 줄로 직렬화된다. JSON의 공백 하나도 서명 계산에 들어가는 바이트이기 때문에, 같은 내용이라도 공백이 다르면 다른 토큰이 된다.

클레임 이름이 세 글자로 짧은 이유: 토큰은 요청마다 전송되므로 크기를 줄이기 위해서다.

### 클레임의 세 종류
| 종류 | 설명 | 예시 |
|---|---|---|
| 등록된 클레임 (Registered) | RFC 7519가 이름과 의미를 정해 둔 클레임. 모두 선택 사항이다. | `iss`, `sub`, `exp` |
| 공개 클레임 (Public) | 여러 서비스가 함께 쓰려고 IANA에 등록했거나, 충돌하지 않게 URI 형태로 지은 클레임 | `email`, `name`, `https://blog.com/claims/role` |
| 비공개 클레임 (Private) | 토큰을 주고받는 당사자끼리만 약속한 클레임 | 이 프로젝트의 `id` |

> **IANA란?**
> Internet Assigned Numbers Authority. 인터넷에서 쓰는 이름과 번호(포트 번호, 도메인 최상위 이름, JWT 클레임 이름 등)를 등록하고 관리하는 기관이다.

### 등록된 클레임 (Registered Claims)
| 클레임 | 이름 | 값의 형식 | 의미 | 검증할 때 |
|---|---|---|---|---|
| `iss` | Issuer | 문자열 | 토큰 **발급자** | 기대하는 발급자와 같은지 확인 |
| `sub` | Subject | 문자열 | 토큰의 **주체**. 이 토큰이 누구에 대한 것인지. 발급자 안에서 겹치지 않아야 한다. | 사용자 식별에 사용 |
| `aud` | Audience | 문자열 또는 문자열 배열 | 토큰의 **수신 대상**. 이 토큰을 받아서 처리할 서비스 | 자기 자신이 목록에 없으면 **거부해야 한다** |
| `exp` | Expiration Time | NumericDate | **만료 시각**. 이 시각 이후에는 받아들이면 안 된다. | `현재 시각 < exp`인지 확인 |
| `nbf` | Not Before | NumericDate | **사용 시작 시각**. 이 시각 전에는 받아들이면 안 된다. | `현재 시각 >= nbf`인지 확인 |
| `iat` | Issued At | NumericDate | **발급 시각** | 토큰의 나이 계산에 사용 |
| `jti` | JWT ID | 문자열 | 토큰의 **고유 번호** | 같은 토큰의 재사용 탐지, 차단 목록에 사용 |

### NumericDate 형식
`1970-01-01T00:00:00Z`(UTC)부터 지난 **초**를 숫자로 나타낸다. 밀리초가 아니라 **초**다.
```
iat: 1790996400  →  2026-10-03 03:00:00 UTC  =  2026-10-03 12:00:00 KST
exp: 1791003600  →  2026-10-03 05:00:00 UTC  =  2026-10-03 14:00:00 KST
exp - iat = 7200초 = 2시간
```
Java의 `Date`나 `System.currentTimeMillis()`는 밀리초 단위이므로, JWT 라이브러리가 1000으로 나눈 값을 넣는다.

> **시계 오차 (Clock Skew)**
> 토큰을 발급한 서버와 검증하는 서버의 시계가 몇 초 다를 수 있다. 그래서 `exp`, `nbf`를 검사할 때 보통 30초~수 분 정도의 여유(leeway)를 둔다.

## 6. 서명 (Signature)
헤더와 페이로드가 바뀌지 않았음을 증명하는 값이다.
```
서명 입력 = ASCII( Base64URL(헤더) + "." + Base64URL(페이로드) )
서명      = 서명 알고리즘( 키, 서명 입력 )
토큰      = Base64URL(헤더) + "." + Base64URL(페이로드) + "." + Base64URL(서명)
```
중요한 점은 **원본 JSON이 아니라 Base64URL로 인코딩한 문자열에 서명한다**는 것이다. 그래서 검증할 때 JSON을 다시 만들 필요 없이, 받은 문자열 그대로 다시 계산하면 된다.

서명 알고리즘의 내부 동작과 검증 절차는 [JWT의 서명과 검증](./05_jwt_signature_and_validation.md)에서 자세히 본다.

## 7. JWT를 만드는 과정 (HS256 기준)
```
1. 헤더 JSON 만들기
   {"typ":"JWT","alg":"HS256"}                                   (27바이트)

2. 헤더를 UTF-8 바이트로 바꾸고 Base64URL 인코딩
   eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9                           (36글자)

3. 페이로드 JSON 만들기
   {"iss":"issue@antimony.kr","iat":1790996400,"exp":1791003600,"sub":"a@a.com","id":1}   (84바이트)

4. 페이로드를 Base64URL 인코딩
   eyJpc3MiOiJpc3N1ZUBhbnRpbW9ueS5rciIsImlhdCI6MTc5MDk5NjQwMCwiZXhwIjoxNzkxMDAzNjAwLCJzdWIiOiJhQGEuY29tIiwiaWQiOjF9   (112글자)

5. 서명 입력 = 2번 + "." + 4번                                     (149바이트)

6. HMAC-SHA256(비밀 키, 서명 입력)
   41 1c ba a3 d7 33 82 65 99 c0 94 ca d3 0b 3b 53
   2b 5c c7 03 ce 9e 88 aa 20 67 a8 e9 76 a9 45 74                 (32바이트)

7. 서명을 Base64URL 인코딩
   QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ                    (43글자)

8. 5번 + "." + 7번
   eyJ0eXAi...aWQiOjF9.QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ (193글자)
```

## 8. JWE 형식 (참고)
내용을 숨겨야 할 때 쓰는 암호화된 JWT는 점으로 나뉜 다섯 부분으로 이루어진다.
```
헤더 . 암호화된 키 . 초기화 벡터 . 암호문 . 인증 태그
```
| 부분 | 의미 |
|---|---|
| 헤더 | `alg`(키 암호화 방법), `enc`(내용 암호화 방법) |
| 암호화된 키 | 내용을 암호화한 일회용 키를, 받는 쪽의 키로 다시 암호화한 것 |
| 초기화 벡터 | 같은 내용도 매번 다른 암호문이 되게 섞는 임의의 값 |
| 암호문 | 암호화된 클레임 |
| 인증 태그 | 암호문이 바뀌지 않았음을 확인하는 값 |

인증 용도로는 JWS를 쓰고, 토큰에 민감한 정보를 꼭 넣어야 할 때만 JWE를 검토한다.

## 정리
| 구성 | 내용 |
|---|---|
| 형식 | `Base64URL(헤더).Base64URL(페이로드).Base64URL(서명)` |
| Base64URL | 3바이트 → 6비트 4조각 → 64개 문자. `+/` 대신 `-_`, 패딩 `=` 없음. 암호화 아님 |
| 헤더 | `alg`(필수), `typ`, `kid` 등. 토큰 처리 방법 |
| 페이로드 | 클레임. 등록된 클레임 7개(`iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`) + 공개 + 비공개 |
| 시간 | NumericDate = 1970-01-01 UTC부터의 **초** |
| 서명 | 인코딩된 `헤더.페이로드` 문자열에 대한 서명 |
