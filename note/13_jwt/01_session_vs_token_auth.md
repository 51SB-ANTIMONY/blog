# 세션 기반 인증과 토큰 기반 인증

> 인증, 인가, HTTP의 무상태성, 쿠키와 세션의 기본 개념은 [인증과 인가](../12_spring_security/01_authentication_and_authorization.md)에서 설명했다.

## 1. 출발점: 로그인 상태를 어떻게 유지할 것인가
HTTP는 요청끼리 연결되지 않는다(무상태). 그래서 로그인에 성공한 뒤의 요청마다 "나는 아까 로그인한 사용자다"를 증명할 무언가를 함께 보내야 한다.

이 "무언가"를 무엇으로 하느냐에 따라 인증 방식이 나뉜다.

| 방식 | 매 요청마다 보내는 것 | 그 값의 의미 |
|---|---|---|
| 세션 기반 | 세션 ID | 서버에 저장된 로그인 정보를 찾기 위한 **열쇠 번호**. 값 자체에는 아무 정보가 없다. |
| 토큰 기반 | 토큰 | **로그인 정보 자체**와 그것이 위조되지 않았다는 **증명(서명)**을 함께 담은 값 |

## 2. 세션 기반 인증 (Session-based Authentication)

### 정의
**로그인 정보를 서버에 저장하고, 클라이언트에는 그 저장 위치를 가리키는 세션 ID만 주는 방식**이다.

### 동작
```
[로그인]
클라이언트 ── POST /login (아이디, 비밀번호) ──────────────▶ 서버
                                                         ① 비밀번호 확인
                                                         ② 세션 저장소에 기록
                                                            "9F8E7D..." → {userId: 1, email: a@a.com}
클라이언트 ◀── Set-Cookie: JSESSIONID=9F8E7D... ──────────── 서버

[이후 요청]
클라이언트 ── GET /api/articles ───────────────────────────▶ 서버
             Cookie: JSESSIONID=9F8E7D...                  ③ 세션 저장소에서 "9F8E7D..." 조회
                                                         ④ {userId: 1} 발견 → 인증됨
클라이언트 ◀── 200 OK ───────────────────────────────────── 서버
```

### 세션 ID의 성질
- 서버가 만든 **예측할 수 없는 임의의 문자열**이다. Tomcat은 보안 난수 생성기로 만든 16바이트를 32글자의 16진수 문자열로 바꿔 쓴다.
- 값 자체에는 사용자 정보가 없다. `9F8E7D...`를 보고 누구의 세션인지 알 수 없다.
- 세션 ID를 가진 사람은 그 세션의 주인으로 취급된다. 그래서 세션 ID를 훔치면 로그인 상태를 훔치는 것이 된다.

### 세션 저장소
| 저장소 | 설명 |
|---|---|
| 서버 메모리 | 기본값. Tomcat의 메모리에 저장한다. 서버를 재시작하면 모두 사라진다. |
| 외부 저장소 (Redis, DB) | 여러 서버가 세션을 공유해야 할 때 쓴다. Spring Session 같은 도구로 연결한다. |

### 특징
| 특징 | 설명 |
|---|---|
| 서버가 상태를 가진다 (Stateful) | 로그인한 사용자 수만큼 세션이 서버에 쌓인다. |
| 즉시 무효화가 쉽다 | 세션을 지우면 그 순간부터 그 세션 ID는 쓸모없어진다. 강제 로그아웃, 비밀번호 변경 시 전체 로그아웃이 쉽다. |
| 요청이 작다 | 매 요청마다 32글자 정도의 세션 ID만 보낸다. |
| 매 요청마다 저장소 조회가 필요하다 | 세션 ID로 세션을 찾는 작업이 요청마다 일어난다. |
| 서버를 늘리기 어렵다 | 서버가 여러 대면 세션을 서로 공유해야 한다(3장). |
| 쿠키에 의존한다 | 브라우저가 쿠키를 자동으로 보내므로 편하지만, 그 때문에 CSRF 방어가 필요하다. 쿠키를 다루기 어려운 환경(모바일 앱, 다른 도메인의 API)에서는 불편하다. |

## 3. 토큰 기반 인증 (Token-based Authentication)

### 정의
**로그인에 성공하면 서버가 사용자 정보를 담은 토큰을 발급하고, 클라이언트가 이후 요청마다 그 토큰을 보내면 서버는 토큰 자체를 검사해서 인증하는 방식**이다.

> **토큰(Token)이란?**
> 인증 분야에서는 "이 요청을 보낸 사람이 인증된 사용자임을 나타내는 값"을 말한다. 토큰을 가지고 요청하는 것이 곧 권한을 증명하는 것이 된다.

### 동작
```
[로그인]
클라이언트 ── POST /login (아이디, 비밀번호) ──────────────▶ 서버
                                                         ① 비밀번호 확인
                                                         ② 토큰 생성
                                                            {userId: 1, 만료: 14:00} + 서명
                                                            (서버에 저장하지 않음)
클라이언트 ◀── {"accessToken": "eyJ..."} ────────────────── 서버
③ 토큰 저장

[이후 요청]
클라이언트 ── GET /api/articles ───────────────────────────▶ 서버
             Authorization: Bearer eyJ...                  ④ 서명 검사 → 위조되지 않음
                                                         ⑤ 만료 시각 검사 → 아직 유효
                                                         ⑥ 토큰 안의 {userId: 1} 사용
클라이언트 ◀── 200 OK ───────────────────────────────────── 서버
```
④~⑥에서 서버는 **어떤 저장소도 조회하지 않는다.** 토큰에 필요한 정보가 다 들어 있고, 서명으로 그 정보가 진짜임을 확인할 수 있기 때문이다.

### 토큰의 종류
| 종류 | 설명 | 서버의 검증 방법 |
|---|---|---|
| 자체 포함 토큰 (self-contained) | 토큰 안에 사용자 정보와 서명이 들어 있다. **JWT**가 대표적이다. | 서명과 만료 시각만 검사한다. 저장소 조회가 없다. |
| 불투명 토큰 (opaque) | 의미 없는 임의의 문자열이다. 세션 ID와 비슷하다. | 저장소에서 토큰을 조회하거나, 발급한 인증 서버에 물어본다. |

"토큰 기반 인증의 특징"이라고 하면 보통 자체 포함 토큰, 즉 JWT를 쓰는 경우를 말한다. 이 폴더의 노트도 JWT를 기준으로 한다.

### 특징
| 특징 | 설명 |
|---|---|
| 서버가 상태를 갖지 않는다 (Stateless) | 서버는 발급한 토큰을 기억하지 않는다. |
| 서버를 늘리기 쉽다 | 비밀 키(또는 공개 키)만 있으면 어느 서버든 토큰을 검증할 수 있다. |
| 위조를 알아낼 수 있다 | 서명 덕분에 토큰 내용이 바뀌면 검증에서 걸린다. |
| 즉시 무효화가 어렵다 | 서버가 토큰을 기억하지 않으므로, 이미 발급한 토큰을 만료 전에 막을 방법이 기본적으로 없다. |
| 요청이 크다 | 토큰에 정보가 들어 있어서 세션 ID보다 훨씬 길다(보통 수백 바이트). |
| 내용이 공개된다 | JWT의 내용은 암호화가 아니라 인코딩이다. 누구나 읽을 수 있으므로 비밀 정보를 넣으면 안 된다. |
| 쿠키에 의존하지 않는다 | 클라이언트가 직접 헤더에 넣어 보내므로 모바일 앱, 다른 도메인의 API에서도 똑같이 쓸 수 있다. |

## 4. 한눈에 비교
| 항목 | 세션 기반 | 토큰 기반 (JWT) |
|---|---|---|
| 로그인 정보 저장 위치 | 서버 (세션 저장소) | 토큰 안 (클라이언트가 보관) |
| 클라이언트가 보내는 값 | 세션 ID (의미 없는 임의 문자열) | 토큰 (정보 + 서명) |
| 보내는 방법 | `Cookie` 헤더 (브라우저가 자동으로) | 보통 `Authorization: Bearer` 헤더 (코드가 직접) |
| 서버의 인증 작업 | 저장소에서 세션 조회 | 서명 계산, 만료 시각 비교 |
| 서버 상태 | 있음 (Stateful) | 없음 (Stateless) |
| 서버 여러 대 | 세션 공유 필요 | 키만 공유하면 됨 |
| 강제 로그아웃 | 세션 삭제로 즉시 | 어려움. 짧은 만료 시간 + 리프레시 토큰으로 보완 |
| 요청 크기 | 작음 (수십 바이트) | 큼 (수백 바이트) |
| CSRF | 쿠키 자동 전송 때문에 방어 필요 | 헤더로 보내면 해당 없음 |
| 주 사용처 | 서버가 HTML을 만드는 전통적인 웹사이트 | 모바일 앱, SPA(React 등), 여러 서비스로 나뉜 시스템 |

> **SPA란?**
> Single Page Application. 처음에 HTML 한 장을 받고, 이후에는 JavaScript가 API에서 JSON만 받아 화면을 바꾸는 웹 애플리케이션이다. React, Vue로 만든 앱이 여기에 해당한다.

두 방식의 차이가 실제로 어떤 결과를 낳는지는 [토큰 기반 인증의 특징](./03_token_auth_characteristics.md)에서 예시로 비교한다.
