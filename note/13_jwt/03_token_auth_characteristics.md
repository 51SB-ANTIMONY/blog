# 토큰 기반 인증의 특징 - 무상태성, 확장성, 무결성

> 세션 방식과 토큰 방식의 기본 비교는 [세션 기반 인증과 토큰 기반 인증](./01_session_vs_token_auth.md)에서 했다.
> 이 노트는 토큰 방식의 세 가지 특징을 **같은 상황에서 두 방식이 어떻게 다르게 동작하는지** 예시로 비교한다.

## 1. 무상태성 (Statelessness)

### 정의
**서버가 클라이언트의 인증 상태를 저장하지 않는 성질**이다. 요청 하나에 인증에 필요한 정보가 모두 들어 있어서, 서버는 그 요청만 보고 판단할 수 있다.

> **상태(State)란?**
> 이전 요청의 결과로 서버에 남아 있는 정보를 말한다. "사용자 A가 10시에 로그인했다"는 기록이 서버에 남아 있다면 서버는 상태를 가진 것이다.

### 예시: 서버가 재시작되면
상황: 사용자 A가 로그인한 뒤, 서버를 새 버전으로 배포하느라 재시작했다.

**세션 방식 (메모리 저장)**
```
10:00  A 로그인 → 서버 메모리: { "9F8E..." → A }
10:30  서버 재시작 → 메모리 초기화: { }
10:31  A의 요청 (Cookie: JSESSIONID=9F8E...)
       → 서버: "9F8E..."라는 세션 없음 → 익명 사용자 → 로그인 페이지로
```
A는 아무것도 하지 않았는데 로그아웃된다. 세션을 Redis 같은 외부 저장소에 두면 피할 수 있지만, 그만큼 관리할 대상이 늘어난다.

**토큰 방식**
```
10:00  A 로그인 → 토큰 발급 (서버에는 아무것도 저장하지 않음)
10:30  서버 재시작 → 비밀 키는 설정 파일에 그대로 있음
10:31  A의 요청 (Authorization: Bearer eyJ...)
       → 서버: 비밀 키로 서명 검사 → 통과 → 만료 전 → A로 인증
```
서버가 기억하던 것이 없으므로 재시작해도 잃을 것이 없다. 비밀 키만 같으면 된다.

### 비교
| 항목 | 세션 방식 | 토큰 방식 |
|---|---|---|
| 서버가 저장하는 것 | 로그인한 사용자마다 세션 1개 | 없음 (비밀 키 1개만) |
| 동시 접속자 10만 명 | 세션 10만 개가 메모리나 저장소에 존재 | 서버 저장 공간 변화 없음 |
| 인증할 때 필요한 것 | 요청 + 서버의 세션 저장소 | 요청 하나 + 비밀 키 |
| 서버 재시작 | 메모리 세션이면 전원 로그아웃 | 영향 없음 |

### 무상태성의 대가
서버가 기억하지 않는다는 것은 **서버가 토큰을 취소할 수도 없다**는 뜻이다.

상황: A의 토큰이 탈취됐다. 관리자가 A를 즉시 로그아웃시키려 한다.
- 세션 방식: A의 세션을 삭제한다. 공격자의 다음 요청부터 바로 막힌다.
- 토큰 방식: 서버는 그 토큰을 기억하지 않으므로 지울 대상이 없다. 토큰은 만료 시각까지 계속 유효하다.

그래서 토큰 방식은 다음으로 보완한다.
- 액세스 토큰의 유효 시간을 짧게 한다(수 분~수 시간).
- 오래 쓰는 리프레시 토큰은 서버에 저장해서, 필요하면 지운다([리프레시 토큰](./06_refresh_token.md)).
- 꼭 즉시 막아야 하면 "차단된 토큰 목록"을 서버에 둔다. 이렇게 하면 이 부분만큼은 다시 상태를 갖게 된다.

## 2. 확장성 (Scalability)

### 정의
**사용자가 늘어날 때 서버를 추가해서 처리량을 쉽게 늘릴 수 있는 성질**이다.

> **스케일 아웃(Scale-out)이란?**
> 서버 한 대의 성능을 올리는 대신, 같은 서버를 여러 대로 늘려 요청을 나눠 처리하는 방법이다.

> **로드 밸런서(Load Balancer)란?**
> 들어오는 요청을 여러 서버에 나눠 보내는 장비나 프로그램이다.

### 예시: 서버 3대로 늘렸을 때
```
                         ┌──▶ 서버 1
클라이언트 ──▶ 로드 밸런서 ┼──▶ 서버 2
                         └──▶ 서버 3
```
상황: A가 로그인 요청을 보냈고 로드 밸런서가 서버 1로 보냈다. 다음 요청은 서버 2로 갔다.

**세션 방식 (각 서버 메모리에 저장)**
```
요청 1: POST /login        → 서버 1: 세션 생성 { "9F8E..." → A }
요청 2: GET /api/articles  → 서버 2: "9F8E..."? 모르는 세션 → 로그인 페이지로
```
서버 2는 서버 1의 메모리를 볼 수 없다. 해결 방법은 다음과 같고, 각각 비용이 있다.

| 해결 방법 | 내용 | 단점 |
|---|---|---|
| 고정 세션 (Sticky Session) | 로드 밸런서가 같은 사용자를 항상 같은 서버로 보낸다. | 서버 1이 죽으면 그 서버의 사용자는 모두 로그아웃. 요청이 고르게 나뉘지 않는다. |
| 세션 복제 | 서버끼리 세션을 서로 복사한다. | 서버가 늘수록 복사량이 늘어난다. |
| 외부 세션 저장소 | 모든 서버가 Redis 하나에 세션을 저장하고 조회한다. | 요청마다 Redis 조회. Redis가 멈추면 전체 인증이 멈춘다. |

**토큰 방식**
```
요청 1: POST /login        → 서버 1: 토큰 발급 (저장 없음)
요청 2: GET /api/articles  → 서버 2: 같은 비밀 키로 서명 검사 → 통과 → A
요청 3: GET /api/articles  → 서버 3: 같은 비밀 키로 서명 검사 → 통과 → A
```
어느 서버로 가든 결과가 같다. 서버끼리 주고받을 것도 없고, 공유 저장소도 필요 없다. 서버를 100대로 늘려도 각 서버에 같은 비밀 키만 설정하면 된다.

### 예시: 서비스가 여러 개로 나뉠 때
블로그를 "글 서비스", "댓글 서비스", "알림 서비스"로 나눠 각각 다른 서버에서 운영한다고 하자.
- 세션 방식: 세 서비스가 모두 같은 세션 저장소에 접근해야 한다. 서비스끼리 저장소를 공유하게 되어 서로 묶인다.
- 토큰 방식: 인증 서버 하나가 토큰을 발급하고, 나머지 서비스는 토큰을 검증만 한다. 서명을 **공개 키 방식(RS256 등)**으로 만들면, 각 서비스는 공개 키만 가지고 검증할 수 있다. 토큰을 만들 수 있는 비밀 키는 인증 서버에만 있다([JWT의 서명과 검증](./05_jwt_signature_and_validation.md)).

### 예시: 다른 도메인, 모바일 앱
- 쿠키는 기본적으로 쿠키를 준 도메인으로 가는 요청에만 붙는다. 프론트엔드(`blog.com`)와 API 서버(`api.blog.com`)가 다르면 쿠키 설정이 복잡해진다.
- 모바일 앱은 브라우저처럼 쿠키를 자동으로 관리하지 않는다.
- 토큰은 코드가 직접 `Authorization` 헤더에 넣으므로 도메인, 클라이언트 종류와 상관없이 같은 방식으로 동작한다.

### 비교
| 항목 | 세션 방식 | 토큰 방식 |
|---|---|---|
| 서버 추가 시 필요한 작업 | 세션 공유 방법 마련 | 비밀 키(또는 공개 키) 설정 |
| 요청마다 외부 저장소 조회 | 외부 저장소를 쓰면 필요 | 불필요 |
| 서버 한 대 장애 시 | 고정 세션이면 그 서버 사용자 로그아웃 | 영향 없음 |
| 여러 서비스 간 인증 | 저장소 공유 필요 | 토큰 검증만 하면 됨 |

### 확장성의 대가
- 요청마다 토큰을 보내므로 네트워크 사용량이 늘어난다. 세션 ID 53바이트 대신 토큰 헤더 200~1000바이트.
- 요청마다 서명 계산을 한다. HS256은 매우 빠르지만, 세션 ID로 메모리를 한 번 조회하는 것보다는 일이 많다.

## 3. 무결성 (Integrity)

### 정의
**데이터가 만들어진 뒤 바뀌지 않았음을 보장하는 성질**이다. 토큰 방식에서는 **서명**으로 무결성을 보장한다.

> **서명(Signature)이란?**
> 데이터와 비밀 키를 함께 계산해서 만든 값이다. 비밀 키를 모르면 올바른 서명을 만들 수 없고, 데이터가 한 글자라도 바뀌면 서명이 완전히 달라진다.

### 왜 토큰에 무결성이 필요한가
토큰 방식에서는 **사용자 정보가 클라이언트 손에 있다.** 클라이언트는 그 토큰을 마음대로 바꿔서 보낼 수 있다. 서버가 토큰 내용을 그대로 믿으면 다음이 가능해진다.

### 예시: 토큰의 사용자 id를 바꿔 보낸다
A(id=1)가 받은 토큰의 내용 부분:
```json
{"iss":"issue@antimony.kr","iat":1790996400,"exp":1791003600,"sub":"a@a.com","id":1}
```
A가 이것을 `"id":2`로 고쳐서 Base64URL로 다시 인코딩한 뒤, 원래 서명을 그대로 붙여 보낸다.
```
eyJ0eXAi...(헤더 그대로) . eyJpc3Mi...(id를 2로 바꾼 내용) . QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ(원래 서명)
```
서버의 검증:
```
1. 받은 헤더 + 바뀐 내용으로 서명을 다시 계산
   → qnEbOo7IJektPQPQC5ADbWvDlobzrxZs2YGgEoL4Jns
2. 받은 서명과 비교
   → QRy6o9czgmWZwJTK0ws7UytcxwPOnoiqIGeo6XapRXQ
3. 다르다 → 위조된 토큰 → 401
```
A가 올바른 서명을 새로 만들려면 서버의 비밀 키가 필요하다. 비밀 키는 서버에만 있으므로 불가능하다. 숫자 `1`을 `2`로 바꾼 것뿐인데 서명이 완전히 다른 값이 된다는 점에 주목한다. 이것이 해시 함수의 성질이다([JWT의 서명과 검증](./05_jwt_signature_and_validation.md)).

### 세션 방식에서는 무결성을 어떻게 보장하나
세션 방식은 **사용자 정보를 클라이언트에 주지 않는 방식**으로 무결성 문제를 피한다.
- 클라이언트가 가진 것은 세션 ID뿐이다. 사용자 정보는 서버에 있으므로 클라이언트가 바꿀 수 없다.
- 세션 ID를 바꿔서 보내면? 세션 ID는 16바이트(128비트) 난수라서 다른 사람의 세션 ID를 맞힐 확률은 2^128분의 1 수준이다. 바꾼 값은 존재하지 않는 세션이 되어 익명 사용자로 처리된다.

| 항목 | 세션 방식 | 토큰 방식 |
|---|---|---|
| 사용자 정보의 위치 | 서버 | 클라이언트 (토큰 안) |
| 클라이언트가 바꿀 수 있는 것 | 세션 ID | 토큰 전체 |
| 바꿨을 때 | 존재하지 않는 세션 → 익명 | 서명 불일치 → 거부 |
| 무결성을 보장하는 수단 | 정보를 주지 않음 + 추측 불가능한 ID | 서명 |

### 무결성은 기밀성이 아니다
> **기밀성(Confidentiality)이란?**
> 허락받지 않은 사람이 데이터의 내용을 **읽을 수 없게** 하는 성질이다.

서명은 "바뀌지 않았음"을 보장할 뿐, "읽을 수 없음"을 보장하지 않는다. JWT의 내용은 Base64URL로 인코딩만 되어 있어서 누구나 디코딩해서 읽을 수 있다.
```
eyJpc3MiOiJpc3N1ZUBhbnRpbW9ueS5rciIsImlhdCI6...
  → Base64URL 디코딩 →
{"iss":"issue@antimony.kr","iat":1790996400,...,"sub":"a@a.com","id":1}
```
그래서 토큰에는 비밀번호, 주민등록번호 같은 정보를 넣으면 안 된다. 내용을 숨겨야 한다면 JWE(암호화된 JWT)를 쓴다([JWT의 구조](./04_jwt_structure.md)).

## 정리
| 특징 | 의미 | 세션 방식과의 차이 | 대가 |
|---|---|---|---|
| 무상태성 | 서버가 인증 상태를 저장하지 않는다 | 세션 저장소가 필요 없다. 서버 재시작에 영향이 없다. | 발급한 토큰을 즉시 취소하기 어렵다 |
| 확장성 | 서버를 늘려도 추가 작업이 거의 없다 | 세션 공유가 필요 없다. 여러 서비스, 모바일 앱에서도 같은 방식 | 요청이 커진다 |
| 무결성 | 서명으로 내용이 바뀌지 않았음을 보장한다 | 세션은 정보를 주지 않는 방식으로, 토큰은 서명으로 보장 | 내용은 누구나 읽을 수 있다 |
