# accounts 분리하기 - 7단계 아이디·비밀번호 설정과 변경 (계획)

> 전체 단계는 [로드맵](./01_roadmap.md)에 있다. 배포 뒤 브라우저 확인에서 나온 문제를 다룬다.

## 1. 목적
accounts의 **내 계정** 화면에서 아이디와 비밀번호를 정하고 바꿀 수 있게 한다.

### 배포 뒤 확인에서 나온 문제
| 문제 | 지금 동작 |
|---|---|
| 소셜(Google)로만 가입한 회원 | 아이디가 `google_3f9a2c1b`처럼 자동으로 정해지고 비밀번호가 없다. 내 계정에 "아이디·비밀번호 설정 안 됨"이 뜬다 |
| 그 옆의 "비밀번호 설정" 버튼 | **비밀번호 찾기** 화면(`/reset-password`)으로 간다. 비밀번호 찾기는 아이디와 이메일 인증번호를 묻는데, 자동 아이디를 모르는 회원은 쓸 수 없다. 아이디도 정할 수 없다 |
| 비밀번호가 있는 회원의 "비밀번호 변경" 버튼 | 같은 비밀번호 찾기 화면으로 간다. 로그인한 상태인데도 메일 인증을 다시 해야 한다 |
| 소셜 연결 해제 | 비밀번호가 없는 회원이 마지막 소셜 계정을 해제하려 하면 "비밀번호 찾기로 비밀번호를 먼저 설정해 주세요"라고 안내한다. 위의 이유로 그 안내대로 할 수 없다 |

## 2. 정한 것
| 질문 | 결정 |
|---|---|
| 소셜로만 가입한 회원 | 새 화면 **아이디·비밀번호 설정**에서 아이디와 비밀번호를 **함께** 정한다. 이미 로그인한 상태이므로 현재 비밀번호나 메일 인증은 묻지 않는다 |
| 아이디 변경 | **처음 설정할 때만**. 소셜 회원이 아이디·비밀번호를 처음 정할 때 자동 아이디를 바꿀 수 있고, 그 뒤로는 바꿀 수 없다. 아이디·비밀번호로 가입한 회원은 가입 때 정한 아이디 그대로다 |
| 비밀번호가 있는 회원의 비밀번호 변경 | 새 화면 **비밀번호 변경**에서 **현재 비밀번호 + 새 비밀번호**. 현재 비밀번호를 잊었으면 기존 비밀번호 찾기(메일 인증)를 쓴다 |

결정에서 나오는 규칙: **아이디를 바꿀 수 있는 것은 비밀번호가 없는 회원뿐이고, 아이디와 비밀번호는 한 번에 함께 정해진다.** 서버는 "비밀번호가 없는가"만 보면 된다.

아이디를 바꿔도 다른 앱에는 영향이 없다. blog 등은 아이디가 아니라 회원 번호(ID 토큰의 `sub` = `accounts.users.id`)로 회원을 구별하고, `blog.users`에는 이 번호(`accounts_sub`)와 닉네임만 저장한다.

## 3. 세부 단계

### 7-1. 프로토타입 ("ANTIMONY 로그인 · 회원가입" 아티팩트)
화면을 코드에서 즉흥적으로 정하지 않는다는 원칙에 따라, 프로토타입에 먼저 만든다. PC와 모바일, 라이트와 다크 모드를 함께 만든다.

| 화면 | 들어오는 곳 | 입력 |
|---|---|---|
| 아이디·비밀번호 설정 | 내 계정 → (비밀번호 없는 회원) "아이디·비밀번호 설정" | 아이디(중복 확인, 지금 자동 아이디를 안내), 비밀번호, 비밀번호 확인 |
| 비밀번호 변경 | 내 계정 → (비밀번호 있는 회원) "비밀번호 변경" | 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인. "비밀번호를 잊었나요?" → 비밀번호 찾기 |

- 입력 규칙은 회원가입과 같다. 아이디는 영문 소문자·숫자 4–16자, 비밀번호는 8자 이상·영문과 숫자·특수문자 포함. 회원가입 화면의 구성 요소(비밀번호 입력, 조건 표시)를 그대로 쓴다.
- 완료하면 내 계정으로 돌아와 "아이디와 비밀번호를 설정했어요" / "비밀번호를 바꿨어요" 안내를 띄운다.
- 내 계정의 "아이디" 줄에, 비밀번호가 없는 회원에게는 "자동으로 만든 아이디예요" 같은 안내를 둔다.

**결과 (프로토타입 버전 11):** 화면 줄 2개(PC·모바일 × 라이트·다크, 8개)를 추가하고 내 계정을 고쳤다.
| 화면 | 내용 |
|---|---|
| 내 계정 | Tweaks의 `member`(password / social)로 회원 종류를 바꿔 본다. social이면 아이디 아래 "자동으로 만든 아이디", 상태 "설정 안 됨", 버튼 "아이디·비밀번호 설정". social에서 마지막 소셜 계정을 해제하면 "아이디·비밀번호를 먼저 설정해 주세요" 오류 |
| 아이디·비밀번호 설정 | 지금 아이디와 "한 번만 정할 수 있어요" 안내, 새 아이디(중복확인), 비밀번호와 조건 표시, 비밀번호 확인, "설정 완료", "내 계정으로 돌아가기" |
| 비밀번호 변경 | 현재 비밀번호와 "비밀번호 찾기" 링크, 새 비밀번호와 조건 표시, 새 비밀번호 확인, "비밀번호 변경", "내 계정으로 돌아가기". 새 비밀번호가 현재와 같으면 오류. 현재 비밀번호 칸에 `wrong1!`을 넣으면 서버가 틀렸다고 응답한 경우를 보여 준다 |

안내 문구와 완료 뒤 동작은 캔버스의 메모에 적었다.

### 7-2. 서버 API (accounts backend)
| API | 조건 | 하는 일 |
|---|---|---|
| `GET /api/me/uid-availability?uid=` | 로그인 | 아이디 형식·중복 확인. 회원가입의 중복 확인과 같은 규칙(가입 신청 중인 아이디도 사용 중으로 본다) |
| `POST /api/me/credentials` `{uid, password}` | 로그인, **비밀번호 없는 회원만** | 아이디와 비밀번호 해시를 함께 저장. 비밀번호가 이미 있으면 409 |
| `PUT /api/me/password` `{currentPassword, newPassword}` | 로그인, 비밀번호 있는 회원 | 현재 비밀번호 확인 후 새 비밀번호 해시 저장. 현재 비밀번호가 틀리거나 새 비밀번호가 현재와 같으면 400, 비밀번호가 없으면 409 |

- 형식 검사는 회원가입의 `SignupRequest`와 같은 규칙(`PasswordRule`, 아이디 정규식)을 쓴다.
- 소셜 연결 해제의 안내 문구를 "아이디·비밀번호를 먼저 설정해 주세요"로 바꾼다.
- **로그인 상태 유지(remember-me)**: 이 서버의 로그인 유지 쿠키는 비밀번호 해시로 서명된다. 비밀번호를 바꾸면 다른 기기의 로그인 유지 쿠키는 자동으로 무효가 된다. 지금 세션은 유지된다.
- 테스트: 비밀번호 없는 회원의 설정 성공, 이미 비밀번호가 있으면 거절, 아이디 중복·형식 오류, 현재 비밀번호 틀림, 변경 후 새 비밀번호로 로그인되는지, 로그인하지 않은 요청은 401.

### 7-3. 화면 (accounts frontend)
- `/account/credentials` (아이디·비밀번호 설정), `/account/password` (비밀번호 변경)를 프로토타입대로 만든다. 탭 제목은 `Antimony Set Credentials`, `Antimony Change Password`.
- 내 계정의 버튼 연결을 바꾼다: 비밀번호 없음 → `/account/credentials`, 있음 → `/account/password`.
- 로그인하지 않은 상태로 들어오면 로그인 화면으로 보낸다(내 계정과 같게).
- 비밀번호가 이미 있는데 설정 화면으로 들어오면 비밀번호 변경 화면으로 보낸다.

### 7-4. 확인
- 자동 테스트(accounts backend), frontend lint·build.
- 로컬에서 실제 흐름: 소셜 회원 → 설정 → 로그아웃 → 새 아이디·비밀번호로 로그인 → 비밀번호 변경 → 새 비밀번호로 로그인.
- push → CI/CD 배포 → 운영에서 같은 흐름.

### 7-5. 기록
이 노트에 결과와 겪은 문제를 적고, 로드맵을 고친다.

### 7-2. 서버에서 바꾼 것
| 파일 | 내용 |
|---|---|
| `service/AccountSettingsService.java` (새 파일) | `checkUid`(회원가입의 `SignupService.checkUid` 재사용), `setCredentials`(비밀번호가 있으면 409, 아이디가 사용 중이면 409 `errors.uid`), `changePassword`(비밀번호 없음 409, 현재 비밀번호 틀림·새 비밀번호가 같음 400) |
| `dto/CredentialsRequest.java`, `dto/PasswordChangeRequest.java` (새 파일) | 형식 검사. 아이디 정규식과 `PasswordRule`은 회원가입과 같다 |
| `domain/User.java` | `setCredentials(uid, passwordHash)`: 아이디와 비밀번호를 함께 바꾼다 |
| `controller/MeApiController.java` | `GET /api/me/uid-availability`, `POST /api/me/credentials`, `PUT /api/me/password` |
| `service/UserService.java` | 마지막 소셜 계정 해제 안내를 "아이디·비밀번호를 먼저 설정해 주세요"로 |

**새 서비스로 나눈 이유:** 아이디 중복확인 규칙은 `SignupService`에 있고, `SignupService`는 `UserService`를 쓴다. `UserService`에 넣어 `SignupService`를 부르면 서로를 부르는 순환 의존이 생긴다.

> **순환 의존이란?**
> A가 B를 필요로 하고 B도 A를 필요로 하는 관계다. Spring은 생성자로 의존성을 넣을 때 어느 쪽을 먼저 만들지 정할 수 없어 서버가 시작하지 못한다.

### 7-4. 확인
**자동 테스트 (accounts 52개 통과, 새로 7개)**
| 테스트 | 확인 |
|---|---|
| 로그인 없이 세 API | 401 |
| 아이디 중복확인 | 형식 오류 invalid, 다른 회원 아이디 taken, 그 밖에 ok |
| 소셜 회원의 설정 | 아이디·비밀번호가 바뀌고, 새 아이디·비밀번호로 로그인되고, **그 뒤 Google 연결을 해제할 수 있다** |

| 설정 입력 오류 | 사용 중인 아이디 409 `errors.uid`, 형식 오류 400, 회원 정보 그대로 |
| 비밀번호 변경 성공 | 새 비밀번호로만 로그인 |

**로컬 실제 흐름 (accounts 서버 + 화면 서버, 화면 서버를 거쳐 요청)**
| 단계 | 결과 |
|---|---|
| 가입 신청 → 인증번호(서버 로그) → 인증 | 201 |
| 아이디·비밀번호 로그인 | `/account`로 이동 |
| 현재 비밀번호를 틀리게 변경 | 400 "현재 비밀번호가 맞지 않아요." |
| 비밀번호가 있는데 설정 API | 409 "이미 아이디와 비밀번호가 설정되어 있어요." |
| 비밀번호 변경 | 204, 지금 세션은 로그인 유지 |
| 다른 세션에서 옛 비밀번호 로그인 | `/login?error=bad_credentials` |
| 새 비밀번호 로그인 | `/account` |
| `/account/credentials`, `/account/password` | 200, 탭 제목 `Antimony Set Credentials`, `Antimony Change Password` |

소셜 회원의 설정 화면 흐름은 Google 로그인이 필요해 로컬에서는 자동 테스트로만 확인했다. 운영에서 Google로 가입한 계정으로 확인한다.

## 6. 추가: 관리자 테이블과 짧은 아이디

### 요청과 정한 것
운영자(운영 DB의 1번 회원)는 4자보다 짧은 아이디를 쓰고 싶다. 처음에는 코드에 `id == 1`을 적었다가 아이디를 정한 뒤 지우는 방법을 검토했다. 나중에 accounts에 관리자 전용 페이지를 만들 예정이어서, 관리자를 데이터로 두기로 했다.

| 검토한 방법 | 판단 |
|---|---|
| 코드에 `id == 1` | id 1은 "그 DB에 처음 가입한 사람"일 뿐이다. 로컬·테스트 DB나 새로 만든 DB에서는 다른 사람이 된다 |
| `users`에 `role` 칸 (USER/ADMIN) | 모든 회원에게 USER 값을 채워야 한다. 관리자는 극소수다 |
| **`admins` 테이블 (선택)** | 관리자만 행을 가진다. 행이 없으면 일반 회원. 관리자 정보(지정 시각 등)를 둘 자리가 있다 |

| 역할 (`admins.role`) | 뜻 |
|---|---|
| `ADMIN` | 관리자 |
| `CO_ADMIN` | 공동 관리자 |
| (행 없음) | 일반 회원 |

관리자(두 역할 모두)는 **아이디·비밀번호 설정에서 1–16자** 아이디를 정할 수 있다. 글자 종류(영문 소문자·숫자), 중복 불가, "처음 한 번만"은 일반 회원과 같다.

### 테이블 (`V4__admins.sql`)
```sql
CREATE TABLE admins (
    user_id    BIGINT      NOT NULL,      -- 기본 키이자 users.id를 가리키는 외래 키
    role       VARCHAR(20) NOT NULL,      -- ADMIN | CO_ADMIN
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (user_id),
    CONSTRAINT fk_admins_user FOREIGN KEY (user_id) REFERENCES users (id)
);

INSERT INTO admins (user_id, role, created_at)
SELECT id, 'ADMIN', CURRENT_TIMESTAMP(6) FROM users WHERE id = 1;
```
- Flyway는 실행한 마이그레이션을 `flyway_schema_history`에 기록하고 다시 실행하지 않는다. 그래서 `INSERT`는 운영 DB에 처음 배포될 때 한 번만 일어난다.
- 회원이 없는 DB(로컬·테스트)에서는 `SELECT`가 아무 행도 돌려주지 않아 관리자가 생기지 않는다.
- 운영 DB의 1번 회원이 운영자 본인인 것은 `/api/me`의 `id`로 확인했다.
- 관리자를 바꾸려면 이 테이블의 행을 넣거나 지운다. 코드는 바꾸지 않는다.

> **외래 키(FOREIGN KEY)란?**
> 이 칸의 값이 다른 테이블에 실제로 있는 값이어야 한다는 제약이다. `admins.user_id`에는 `users`에 있는 회원 번호만 들어갈 수 있다.

## 7. 추가: 이메일 변경

### 정한 것
| 질문 | 결정 |
|---|---|
| 언제 바꿀 수 있나 | **언제든** (아이디와 달리 횟수 제한 없음) |
| 새 이메일 확인 | 새 이메일로 6자리 인증번호 (회원가입·비밀번호 찾기와 같은 규칙: 3분, 5번 틀리면 재전송) |
| 본인 확인을 한 번 더 할까 | **하지 않음.** 로그인 상태와 새 이메일 인증만 |
| 이전 이메일로 알림 | **보냄.** "계정 이메일이 n***@example.com으로 바뀌었어요. 직접 바꾸지 않으셨다면…" |

> **이전 이메일로 알림을 보내는 이유**
> 이메일은 아이디 찾기와 비밀번호 찾기에 쓰인다. 다른 사람이 로그인된 화면에서 이메일을 바꾸면, 그 사람이 비밀번호 찾기로 계정을 가져갈 수 있다. 본인 확인을 한 번 더 하지 않기로 했으므로, 적어도 원래 주인이 바뀐 사실을 알 수 있게 한다.

### 흐름과 API
| 단계 | API | 내용 |
|---|---|---|
| 1 | `POST /api/me/email/code` `{email}` | 지금 이메일과 같으면 400, 다른 회원이 쓰면 409 (`errors.email`). 통과하면 인증번호를 보내고 **새 이메일을 이 로그인 세션에 기록** |
| 2 | `PUT /api/me/email` `{code}` | 세션에 기록된 이메일의 인증번호를 확인. 맞으면 이메일을 바꾸고 이전 이메일로 안내. 세션에 기록이 없으면 400 "인증번호를 먼저 받아 주세요." |

**2단계에서 이메일을 받지 않고 세션에서 꺼내는 이유:** 인증번호는 (목적, 이메일)로 저장된다. 이메일을 요청 본문으로 받으면, 다른 회원이 요청해 둔 인증번호와 엮일 수 있다. 1단계를 요청한 그 로그인 세션만 2단계를 할 수 있게 했다.

> **세션 속성이란?**
> 서버가 로그인 세션마다 따로 저장해 두는 값이다. 이 서버의 세션은 DB(`SPRING_SESSION_ATTRIBUTES`)에 저장되므로, 1단계와 2단계 사이에 서버가 재시작해도 남아 있다.

### 코드
| 파일 | 내용 |
|---|---|
| `domain/VerificationPurpose.java` | `EMAIL_CHANGE` 추가 (`email_verifications.purpose`는 VARCHAR라 테이블 변경 없음) |
| `service/AccountSettingsService.java` | `sendEmailChangeCode`, `changeEmail`. 인증 후 다시 한 번 다른 회원의 이메일인지 확인(그 사이 다른 사람이 같은 이메일로 가입했을 수 있다). 안내 메일이 실패해도 변경은 유지하고 경고 로그만 남긴다 |
| `controller/MeApiController.java` | 두 API. 새 이메일을 세션 속성 `accounts.emailChange`에 기록하고, 변경 후 지운다 |
| `mail/*MailSender.java` | `sendEmailChanged(이전 이메일, 가린 새 이메일)`. SMTP가 없으면 서버 로그에 남긴다 |
| `dto/CodeRequest.java` (새 파일) | 인증번호만 받는 요청 |

| 화면 `AccountView.tsx` | 이메일 줄에 "변경" 링크 |

### 함께 고친 것: 1–2자 아이디의 아이디 찾기
관리자의 짧은 아이디를 허용하면서, 아이디 찾기의 가리기(`maskUid`)가 1자 아이디에서 `"*".repeat(-1)`로 오류가 나는 것을 찾았다. 1–2자는 첫 글자만 보여 주도록 고쳤다(`s` → `s`, `sb` → `s*`).

### 확인
| 확인 | 결과 |
|---|---|
| 프로토타입 | 버전 12. 이메일 변경 화면 4개(PC·모바일 × 라이트·다크), 내 계정 이메일 줄의 "변경" |
| 자동 테스트 | accounts 60개 통과 (새로 4개: 변경 성공과 이전 이메일 안내, 같은 이메일 400·다른 회원 이메일 409·형식 오류 400, 틀린 인증번호 400·인증번호를 요청하지 않은 세션 400, 아이디 가리기) |
| 로컬 실제 흐름 | 가입 → 로그인 → 같은 이메일 400 → 새 이메일 인증번호 → 틀린 번호 400 → 맞는 번호 204 → `/api/me`의 이메일이 바뀜 → 서버 로그에 이전 이메일로 안내 → 새 이메일로 아이디 찾기 인증번호 발송 |

### 트러블슈팅: 테스트에서 세션 속성이 사라졌다
- **증상**: 1단계에서 세션에 넣은 이메일이 2단계에서 없어 400 "인증번호를 먼저 받아 주세요."
- **원인**: 테스트에서 `MockHttpSession`을 넘겼지만, 이 서버는 Spring Session(JDBC)을 쓴다. Spring Session은 요청의 세션을 DB에서 **쿠키(`ACCOUNTS_SESSION`)로** 찾으므로 `MockHttpSession`은 쓰이지 않고 요청마다 새 세션이 만들어졌다.
- **해결**: 1단계 응답의 `ACCOUNTS_SESSION` 쿠키를 꺼내 2단계 요청에 붙였다. 브라우저가 하는 일과 같다.
