# 인증과 인가, 그리고 HTTP에서 로그인 상태를 유지하는 방법

> Spring Security를 이해하려면 먼저 "보안 기능이 무엇을 해결하려는지"를 알아야 한다.
> 이 노트는 Spring과 상관없는 일반 개념을 다루고, 다음 노트부터 Spring Security가 이것을 어떻게 구현하는지 본다.

## 1. 인증 (Authentication)

### 정의
**요청을 보낸 사람이 누구인지 확인하는 과정**이다.

서버에는 요청이 계속 들어온다. 서버는 각 요청에 대해 "이 요청을 보낸 사람이 회원 `a@a.com`이 맞는가?"를 확인해야 한다. 이 확인 과정이 인증이다.

### 인증에 쓰이는 정보
| 종류 | 예시 |
|---|---|
| 사용자가 알고 있는 것 | 비밀번호, PIN 번호 |
| 사용자가 가지고 있는 것 | 휴대폰으로 받은 인증 번호, OTP 기기, 보안 키 |
| 사용자 자신의 특징 | 지문, 얼굴 |

가장 흔한 방식은 **아이디 + 비밀번호**다. 두 가지 이상을 함께 쓰면 **다중 인증(MFA, Multi-Factor Authentication)**이라고 한다.

> **자격 증명(Credentials)이란?**
> 인증에 쓰이는 비밀 정보다. 비밀번호가 대표적이다. Spring Security 코드에서도 `credentials`라는 이름이 나온다.

> **주체(Principal)란?**
> 인증의 대상, 즉 "누구인가"에 해당하는 정보다. 로그인한 사용자 그 자체 또는 사용자 아이디를 가리킨다. Spring Security 코드에서 `principal`이라는 이름으로 나온다.

### 인증의 결과
- 성공: 서버는 "이 요청은 회원 `a@a.com`이 보낸 것"이라고 알게 된다.
- 실패: 서버는 요청을 보낸 사람이 누구인지 모른다. 이런 사용자를 **익명 사용자(anonymous user)**라고 부른다.

## 2. 인가 (Authorization)

### 정의
**인증된 사용자가 요청한 작업을 할 수 있는지 판단하는 과정**이다. 권한 부여, 접근 제어라고도 한다.

예를 들어 이런 규칙들이 인가 규칙이다.
- 글 목록은 로그인한 사용자만 볼 수 있다.
- 관리자 페이지는 관리자 권한이 있는 사용자만 들어갈 수 있다.
- 글 수정은 그 글을 쓴 사람만 할 수 있다.

### 인증과 인가의 순서
인가는 항상 인증 **다음**에 일어난다. "누구인지" 알아야 "무엇을 할 수 있는지" 판단할 수 있기 때문이다.

```
요청 도착
  │
  ▼
[인증] 누구인가?  ──── 알 수 없음 ──▶ 익명 사용자로 취급
  │ 회원 a@a.com
  ▼
[인가] 이 작업을 해도 되는가?
  │                 │
 허용               거부
  ▼                 ▼
작업 실행          에러 응답
```

### 권한을 표현하는 방법
| 용어 | 의미 | 예시 |
|---|---|---|
| 역할 (Role) | 사용자 집단에 붙이는 이름 | `ADMIN`, `USER` |
| 권한 (Authority, Permission) | 할 수 있는 작업 하나하나에 붙이는 이름 | `article:write`, `article:delete` |

Spring Security에서는 둘 다 `GrantedAuthority`라는 하나의 타입으로 다룬다. 역할은 관례상 앞에 `ROLE_`을 붙인다(`ROLE_ADMIN`).

## 3. 인증 실패와 인가 실패: 401과 403
HTTP에는 두 상황을 구분하는 상태 코드가 따로 있다.

| 상태 코드 | 이름 | 의미 | 예시 |
|---|---|---|---|
| `401` | Unauthorized | **인증**이 필요하거나 인증에 실패했다. "당신이 누구인지 모르겠다" | 로그인하지 않고 API 호출 |
| `403` | Forbidden | 인증은 됐지만 **인가**가 거부됐다. "누구인지는 알지만 이 작업은 안 된다" | 일반 회원이 관리자 API 호출 |

`401`의 이름이 "Unauthorized(인가되지 않음)"라서 헷갈리지만, 실제 의미는 "인증되지 않음"이다. HTTP 명세가 만들어질 때 붙은 이름이 그대로 남은 것이다.

> **참고:** 브라우저로 화면을 보는 웹사이트는 로그인이 필요할 때 401 대신 **302 리다이렉트로 로그인 페이지로 보내는** 경우가 많다. 사용자에게 에러 화면보다 로그인 화면을 보여 주는 것이 자연스럽기 때문이다. 이 프로젝트도 이 방식이다.

## 4. HTTP는 상태를 기억하지 않는다 (Stateless)

> **무상태(Stateless)란?**
> 서버가 이전 요청의 내용을 기억하지 않는 성질이다. HTTP에서는 요청 하나하나가 서로 독립적이다.

HTTP 요청은 서로 연결되어 있지 않다. 그래서 다음 문제가 생긴다.

```
요청 1: POST /login  (아이디, 비밀번호)  → 서버: 로그인 성공
요청 2: GET /articles                    → 서버: 이 요청은 누가 보냈지?
```

요청 2에는 로그인 정보가 없다. 서버는 요청 2가 요청 1을 보낸 사람에게서 왔다는 것을 알 수 없다. 그렇다고 매 요청마다 아이디와 비밀번호를 다시 보내게 할 수도 없다.

그래서 **로그인에 성공한 뒤, 이후 요청마다 "나는 아까 로그인한 그 사람이다"를 증명하는 값을 함께 보내는 방법**이 필요하다. 대표적인 방법이 세 가지 있다.

| 방식 | 매 요청마다 보내는 것 | 로그인 정보를 기억하는 곳 |
|---|---|---|
| 세션 + 쿠키 | 세션 ID (쿠키) | 서버 |
| 토큰 (JWT 등) | 토큰 (`Authorization` 헤더) | 토큰 안에 담김 |
| HTTP Basic | 아이디와 비밀번호 (`Authorization` 헤더) | 기억하지 않음 (매번 인증) |

이 프로젝트는 **세션 + 쿠키** 방식을 쓴다. 아래에서 세 방식의 실제 HTTP 형식을 차례로 본다.

## 5. HTTP 메시지의 구조
세 방식을 보기 전에 HTTP 메시지가 어떻게 생겼는지 정리한다. HTTP 메시지는 사람이 읽을 수 있는 텍스트다.

### 요청 (Request)
```http
POST /login HTTP/1.1                                  ← 요청 줄: 메서드, 경로, 버전
Host: localhost:8080                                  ← 헤더 시작
Content-Type: application/x-www-form-urlencoded
Content-Length: 32
Cookie: JSESSIONID=1A2B3C4D5E6F                       ← 헤더 끝
                                                      ← 빈 줄 (헤더와 본문을 구분)
username=a%40a.com&password=1234                      ← 본문 (Body)
```

### 응답 (Response)
```http
HTTP/1.1 302                                          ← 상태 줄: 버전, 상태 코드
Location: /articles                                   ← 헤더 시작
Set-Cookie: JSESSIONID=9F8E7D6C5B4A; Path=/; HttpOnly
Content-Length: 0                                     ← 헤더 끝
                                                      ← 빈 줄
                                                      ← 본문 (이 응답은 비어 있음)
```

> **헤더(Header)란?**
> 요청이나 응답에 붙는 부가 정보다. `이름: 값` 형식으로 한 줄에 하나씩 쓴다.

> **본문(Body)이란?**
> 실제로 전달할 데이터다. 폼 데이터, JSON, HTML 등이 들어간다. 헤더 다음의 빈 줄 뒤에 온다.

이 노트에서 계속 나오는 헤더는 다음과 같다.

| 헤더 | 방향 | 의미 |
|---|---|---|
| `Content-Type` | 요청, 응답 | 본문의 형식 |
| `Location` | 응답 | 리다이렉트할 주소. 3xx 상태 코드와 함께 쓴다. |
| `Set-Cookie` | 응답 | 브라우저에 쿠키를 저장하라는 지시 |
| `Cookie` | 요청 | 브라우저가 저장해 둔 쿠키를 서버에 보냄 |
| `Authorization` | 요청 | 인증 정보 (토큰, Basic 인증 값) |
| `WWW-Authenticate` | 응답 | 401과 함께, 어떤 방식으로 인증해야 하는지 알림 |

## 6. 방식 1: 세션 + 쿠키

### 쿠키 (Cookie)
> **쿠키란?**
> 서버가 브라우저에 저장하라고 보내는 작은 `이름=값` 데이터다. 브라우저는 저장한 쿠키를 같은 서버로 보내는 요청마다 자동으로 붙인다.

**서버 → 브라우저: 쿠키 저장 지시**
```http
Set-Cookie: JSESSIONID=9F8E7D6C5B4A; Path=/; HttpOnly
```

**브라우저 → 서버: 이후 모든 요청에 자동으로 붙임**
```http
Cookie: JSESSIONID=9F8E7D6C5B4A
```

`Set-Cookie`의 `;` 뒤에는 쿠키의 **속성**이 온다.

| 속성 | 의미 |
|---|---|
| `Path=/` | 이 경로 아래로 가는 요청에만 쿠키를 보낸다. `/`면 모든 경로 |
| `HttpOnly` | JavaScript(`document.cookie`)로 이 쿠키를 읽을 수 없게 한다. 악성 스크립트가 세션 ID를 훔치는 것을 막는다. |
| `Secure` | HTTPS 연결에서만 쿠키를 보낸다. |
| `SameSite=Lax` | 다른 사이트에서 시작된 요청에는 쿠키를 보내지 않는다(링크 이동 같은 일부 GET은 예외). CSRF 공격을 줄인다. |
| `Max-Age=3600` | 쿠키를 3600초 동안 유지한다. 이 속성이 없으면 브라우저를 닫을 때 쿠키가 지워진다(세션 쿠키). |

### 세션 (Session)
> **세션이란?**
> 서버가 사용자별로 정보를 저장해 두는 공간이다. 각 세션에는 겹치지 않는 임의의 문자열인 **세션 ID**가 붙는다.

서버 메모리에는 대략 이런 표가 있다.

| 세션 ID | 저장된 정보 |
|---|---|
| `9F8E7D6C5B4A` | 로그인한 사용자: `a@a.com`, 권한: `user` |
| `0A1B2C3D4E5F` | 로그인한 사용자: `b@b.com`, 권한: `user` |

Java 웹 서버(Tomcat 등)는 세션 ID를 `JSESSIONID`라는 이름의 쿠키로 주고받는다.

### 전체 흐름
```
① 로그인 요청
브라우저 ──────────────────────────────────────────▶ 서버
  POST /login
  username=a%40a.com&password=1234
                                                    비밀번호 확인 → 성공
                                                    세션 생성: 9F8E... = {a@a.com}
② 로그인 응답
브라우저 ◀────────────────────────────────────────── 서버
  HTTP/1.1 302
  Set-Cookie: JSESSIONID=9F8E7D6C5B4A; Path=/; HttpOnly
  Location: /articles

  브라우저: 쿠키 저장

③ 이후 요청
브라우저 ──────────────────────────────────────────▶ 서버
  GET /articles
  Cookie: JSESSIONID=9F8E7D6C5B4A
                                                    세션 9F8E... 조회
                                                    → a@a.com이 보낸 요청
```

### 특징
- 로그인 정보가 **서버에** 있다. 브라우저는 의미 없는 세션 ID만 들고 있다.
- 서버가 세션을 지우면 즉시 로그아웃된다. 강제 로그아웃이 쉽다.
- 서버가 여러 대면 세션을 서버끼리 공유해야 하는 문제가 생긴다.
- 쿠키는 브라우저가 **자동으로** 보내므로 CSRF 공격의 대상이 된다(7장).

## 7. 방식 2: 토큰 (Bearer Token)
로그인에 성공하면 서버가 **토큰**(로그인 정보를 담은 서명된 문자열)을 발급한다. 클라이언트는 이후 요청마다 이 토큰을 `Authorization` 헤더에 직접 넣어 보낸다.

```http
GET /api/articles HTTP/1.1
Host: localhost:8080
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhQGEuY29tIn0.Xb3k...
```
- `Bearer`: "이 토큰을 가진 사람(bearer)을 인증해 달라"는 인증 방식 이름이다.
- 토큰 형식으로는 **JWT**(JSON Web Token)를 많이 쓴다. `헤더.내용.서명` 세 부분을 `.`으로 이은 형태다.

> **서명(Signature)이란?**
> 서버만 아는 비밀 키로 만든 값이다. 토큰 내용이 바뀌면 서명이 맞지 않게 되므로, 서버는 토큰이 조작됐는지 알 수 있다.

**특징**
- 로그인 정보가 토큰 안에 있어서 서버가 따로 저장하지 않아도 된다.
- 브라우저가 자동으로 보내지 않고 JavaScript가 직접 헤더에 넣으므로 CSRF 공격의 대상이 아니다.
- 이미 발급한 토큰을 만료 전에 무효로 만들기 어렵다.
- 모바일 앱이나 React 같은 별도 프론트엔드와 함께 쓸 때 많이 쓴다.

## 8. 방식 3: HTTP Basic 인증
매 요청마다 아이디와 비밀번호를 헤더에 넣어 보내는 가장 단순한 방식이다.

**1단계. 인증 없이 요청하면 서버가 401과 인증 방식을 알려 준다**
```http
HTTP/1.1 401
WWW-Authenticate: Basic realm="Realm"
```

**2단계. 클라이언트가 `아이디:비밀번호`를 Base64로 바꿔 보낸다**
```http
GET /api/articles HTTP/1.1
Authorization: Basic YUBhLmNvbToxMjM0
```
`YUBhLmNvbToxMjM0`는 `a@a.com:1234`를 Base64로 바꾼 값이다.

> **Base64란?**
> 데이터를 영문자, 숫자, `+`, `/`로만 이루어진 문자열로 바꾸는 방식이다. **암호화가 아니다.** 누구나 원래 값으로 되돌릴 수 있다.

**특징**
- 비밀번호가 매 요청마다 사실상 그대로 전달되므로 반드시 HTTPS와 함께 써야 한다.
- 로그아웃 개념이 없다.
- 서버끼리의 내부 통신이나 간단한 테스트에 쓴다.

## 9. 세션 + 쿠키 방식에서 알아야 할 공격

### CSRF (Cross-Site Request Forgery)
사용자가 로그인한 상태에서, 공격자가 만든 다른 사이트가 사용자의 브라우저로 이 사이트에 요청을 보내게 만드는 공격이다.

```html
<!-- 공격자 사이트(evil.com)에 숨겨진 폼 -->
<form action="http://localhost:8080/api/articles/1" method="POST">...</form>
<script>document.forms[0].submit();</script>
```
사용자가 `evil.com`을 열면 폼이 자동 제출된다. 브라우저는 `localhost:8080`으로 가는 요청에 `JSESSIONID` 쿠키를 **자동으로** 붙인다. 서버는 정상적인 로그인 사용자의 요청으로 보고 처리한다.

**방어: CSRF 토큰**
서버가 폼을 줄 때 예측할 수 없는 임의의 값(CSRF 토큰)을 숨겨서 넣고, 요청이 오면 이 값이 맞는지 확인한다.
```html
<form action="/login" method="POST">
    <input type="hidden" name="_csrf" value="4bfd1575-3ad1-4d21-96c7-4ef2d9f86721">
    ...
</form>
```
공격자 사이트는 이 값을 알 수 없으므로 올바른 요청을 만들 수 없다. `GET`처럼 데이터를 바꾸지 않는 요청은 검사하지 않고, `POST`, `PUT`, `DELETE`처럼 데이터를 바꾸는 요청만 검사한다.

### 세션 고정 (Session Fixation)
공격자가 자신이 미리 받아 둔 세션 ID를 피해자 브라우저에 심어 두고, 피해자가 그 세션 ID로 로그인하면 공격자도 같은 세션 ID로 로그인 상태를 쓰는 공격이다.

**방어:** 로그인에 성공하는 순간 **세션 ID를 새로 바꾼다.** 공격자가 알던 세션 ID는 쓸모가 없어진다. Spring Security는 이것을 기본으로 해 준다. 그래서 로그인 응답에는 항상 새 `Set-Cookie: JSESSIONID=...`가 들어 있다.

## 10. 비밀번호 저장: 해시
인증에 쓰는 비밀번호는 DB에 **원문으로 저장하면 안 된다.** DB가 유출되면 모든 사용자의 비밀번호가 그대로 드러난다.

> **해시 함수란?**
> 입력값을 정해진 규칙으로 섞어 다른 값으로 바꾸는 함수다. 같은 입력은 항상 같은 결과를 내고, 결과로부터 원래 입력을 계산해 낼 수 없다(단방향).

> **솔트(Salt)란?**
> 해시하기 전에 비밀번호에 섞는 임의의 값이다. 같은 비밀번호라도 솔트가 다르면 해시 결과가 달라진다. 그래서 공격자가 "자주 쓰는 비밀번호의 해시 목록"을 미리 만들어 대조하는 공격이 통하지 않는다.

**저장할 때:** `비밀번호 + 솔트`를 해시해서 저장한다.
**로그인할 때:** 입력한 비밀번호에 저장된 솔트를 섞어 같은 방식으로 해시하고, 저장된 값과 같은지 비교한다.

비밀번호용으로는 **BCrypt**처럼 일부러 계산을 느리게 만든 알고리즘을 쓴다. 공격자가 비밀번호를 하나씩 대입해 보는 속도를 늦추기 위해서다.

BCrypt 결과는 60글자이며 형식은 다음과 같다.
```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │  │  └───── 솔트 22글자 ─────┘└──────── 해시 31글자 ────────┘
 │  └ 비용(cost): 10 → 내부 계산을 2^10번 반복
 └ BCrypt 버전
```
솔트가 결과 안에 들어 있으므로 솔트를 따로 저장할 필요가 없다.

## 정리
| 개념 | 핵심 |
|---|---|
| 인증 | 누구인가를 확인한다. 실패하면 401 (또는 로그인 페이지로 리다이렉트) |
| 인가 | 이 작업을 해도 되는가를 판단한다. 실패하면 403 |
| HTTP 무상태 | 요청끼리 연결되지 않으므로 로그인 상태를 유지하는 방법이 필요하다 |
| 세션 + 쿠키 | 서버가 로그인 정보를 저장하고, 브라우저는 세션 ID 쿠키를 자동으로 보낸다 |
| 토큰 | 로그인 정보를 담은 토큰을 `Authorization: Bearer` 헤더로 보낸다 |
| CSRF | 쿠키 자동 전송을 악용한 공격. CSRF 토큰으로 막는다 |
| 세션 고정 | 로그인 성공 시 세션 ID를 바꿔서 막는다 |
| 비밀번호 저장 | 솔트를 섞어 BCrypt 같은 느린 해시로 저장한다 |
